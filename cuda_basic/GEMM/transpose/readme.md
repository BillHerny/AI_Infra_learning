## 0. TL;DR

| 配置 | V1 naive | V2 tiled | V3 padded | V2/V1 | V3/V1 | V3/V2 |
|---|---|---|---|---|---|---|
| **W=4096**（两阵 128 MiB，DRAM 级） | 1.78 ms / 75 GB/s | 0.94 ms / 143 GB/s | 0.67 ms / 200 GB/s | **1.9x** | **2.7x** | **1.4x** |
| W=4097（非 32 倍数） | 1.33~1.64 ms / 82~101 GB/s | 0.81~0.98 ms / 137~165 GB/s | 0.64~0.74 ms / 182~210 GB/s | 1.6~1.7x | 2.1~2.2x | 1.3x |
| W=1024（两阵 8 MiB，进 L2） | 0.089 ms / 94 GB/s | 0.038 ms / 221 GB/s | 0.022 ms / **390 GB/s** | 2.35x | 4.14x | 1.76x |

（表中为插电档的典型值；各次运行的完整范围见第 1 节。）

三条结论：

1. **V1 → V2（~1.9x）**：消灭了不合并的写。没到理论上 4~5 倍那么夸张 —— L2 会把相邻 warp 写出的 32 B sector 部分攒起来再回写 DRAM，实际放大比理论小，但机理不变。
2. **V2 → V3（~1.3~1.4x）**：`+1` padding 抹掉 store 阶段 32 路 bank conflict 的直接收益。
3. **W=1024 时 V3 = 360~390 GB/s，超过 256 GB/s 的 DRAM 峰值** —— 两个矩阵全在 L2 里，这个数字只反映 L2 带宽，不能用来证明"优化成功"（与 reducemax 的一课相同：规模不够时数字会虚高）。

⚠ **大坑预警**：本机电池供电时 dGPU 被软件限频到 **210~855 MHz**（上限 3105），同一份代码会慢 **4~7 倍**（例：W=4096 的 V1：1.78 ms → 7.24 ms）。跨 session 记录数据前一定先看时钟 —— 详见第 2 节。

## 1. 插电高时钟档的运行结果

> 插电重测（2026-10-13）：`AC1 online = 1`、`BAT1 = Charging`、`SW Power Cap / SW Thermal Slowdown: Not Active`；
> 运行期间后台采样：SM 时钟 **1890~2340 MHz**（空闲时掉到 210）、功率 11~23 W（上限 50 W）。

### 1.1 W = 4096（DRAM 级规模）

插电后两轮会话、共四次运行（均取最快值；#1/#2 为插电后第一轮，#3/#4 为热机后的复核轮）：

| 运行 | V1 naive | V2 tiled | V3 padded | V2/V1 | V3/V1 | V3/V2 |
|---|---|---|---|---|---|---|
| 插电 #1 | 1.7818 ms / 75.3 GB/s | 0.9359 ms / 143.4 GB/s | 0.6716 ms / 199.9 GB/s | 1.90x | 2.65x | 1.39x |
| 插电 #2 | **1.4776 ms / 90.8 GB/s** | **0.8223 ms / 163.2 GB/s** | **0.6349 ms / 211.4 GB/s** | 1.80x | 2.33x | 1.30x |
| 插电 #3 | 1.7818 ms / 75.3 GB/s | 0.9339 ms / 143.7 GB/s | 0.6687 ms / 200.7 GB/s | 1.91x | 2.66x | 1.40x |
| 插电 #4 | 1.7961 ms / 74.7 GB/s | 0.9759 ms / 137.5 GB/s | 0.7322 ms / 183.3 GB/s | 1.84x | 2.45x | 1.33x |

- 典型值 **V1 ≈ 1.78 / V2 ≈ 0.94 / V3 ≈ 0.67 ms**（V3 约 200 GB/s）；#2 的更快数字对应采样里出现的 2340 MHz 窗口；
- ⚠ 就算插了电，**档内仍有 ±10~20% 浮动**（本机 boost 在 1890 / 2130 / 2340 MHz 之间跳）："两遍独立运行差 10%"这条老规矩依旧成立，对比建议交叉测量；
- V1 波动最小（被"写不合并"稳定卡住），V3 波动最大 —— 与之前观测一致；
- **V3 ≈ 200~211 GB/s ≈ 80% 峰值**：转置的访存模式（读 128 B / 写 128 B 交替 + 块间栅栏）比纯流式难喂饱 DRAM，到不了 `vector_add` 的 98%，属正常。

原始输出（插电 #1）：

```
W = 4096  方阵 4096x4096（单阵 64.0 MiB，两阵共 128.0 MiB）
grid = (128, 128), block = (32, 32)
--- 三种 kernel 各跑 20 次、取最快 ---
  V1 naive     best =   1.7818 ms   bandwidth =    75.3 GB/s   verify: PASS
  V2 tiled     best =   0.9359 ms   bandwidth =   143.4 GB/s   verify: PASS
  V3 padded    best =   0.6716 ms   bandwidth =   199.9 GB/s   verify: PASS

加速比（相对 V1）：V2 = 1.90x，V3 = 2.65x
V3 相对 V2（padding 的收益）= 1.39x
```

### 1.2 W = 4097（边界正确性）

```
W = 4097  方阵 4097x4097（单阵 64.0 MiB，两阵共 128.1 MiB）
grid = (129, 129), block = (32, 32)
--- 三种 kernel 各跑 20 次、取最快 ---
  V1 naive     best =   1.3251 ms   bandwidth =   101.3 GB/s   verify: PASS
  V2 tiled     best =   0.8141 ms   bandwidth =   165.0 GB/s   verify: PASS
  V3 padded    best =   0.6411 ms   bandwidth =   209.5 GB/s   verify: PASS

加速比（相对 V1）：V2 = 1.63x，V3 = 2.07x
V3 相对 V2（padding 的收益）= 1.27x
```

W 不是 32 的倍数 → grid 向上取整到 129x129，边缘 tile 靠 `if (x < W && y < W)` 兜底，全 PASS。热机复核轮：1.6435 / 0.9786 / 0.7392 ms（档内偏慢的一轮，规律一致）。

❓ **留个悬念**：V1 在 W=4097 反而比 W=4096 快（1.33~1.64 vs 1.48~1.80 ms，两次会话都出现）。
一个常见解释：4096 的写步长是 2 的幂（16 KiB）→ L2 / DRAM 若发生 **分区冲突（partition camping）**，非 2 的幂步长会把访问打散。真伪留给你用 ncu 验证（看 memory workload 的分区 / sector 分布）。

### 1.3 W = 1024（L2 效应）

```
W = 1024  方阵 1024x1024（单阵 4.0 MiB，两阵共 8.0 MiB）
grid = (32, 32), block = (32, 32)
--- 三种 kernel 各跑 20 次、取最快 ---
  V1 naive     best =   0.0891 ms   bandwidth =    94.2 GB/s   verify: PASS
  V2 tiled     best =   0.0379 ms   bandwidth =   221.2 GB/s   verify: PASS
  V3 padded    best =   0.0215 ms   bandwidth =   390.1 GB/s   verify: PASS

加速比（相对 V1）：V2 = 2.35x，V3 = 4.14x
V3 相对 V2（padding 的收益）= 1.76x
```

- V3 的 **390 GB/s 远超 256 GB/s 峰值**：8 MiB 全在 L2 里，跑的是 L2 带宽（热机复核轮同样超峰：360.6 GB/s）；
- 此时 V2 只有 221 GB/s —— **bank conflict 把 V2 卡在 SM 一侧**，L2 的红利被吃掉大半；
- 启示：**L2 级规模适合放大"SM 内部手艺"的差异（padding、冲突）；DRAM 级规模才适合测"带宽"。**

## 5. 附录 A：`blockIdx.x` / `blockIdx.y` 详解

> 学习答疑整理（2026-10-13）。本练习是工程里第一次用二维网格，这一节把"我是谁、我负责哪格"的编号系统完整讲一遍。

### 5.1 一句话

`blockIdx.x` = 这一块在大网格里的**横向**编号（第几列块）；`blockIdx.y` = **纵向**编号（第几行块）。就像在地图上报"第几列、第几行"。

### 5.2 GPU 干活的"三层组织"

```
grid（网格）      = 整个工程队      → 由一堆 block 组成
  block（块）    = 一个班组        → 由一堆 thread 组成
    thread（线程）= 一个工人        → 干最小的活
```

启动时的 `<<<grid, block>>>` 就是定义这棵组织树：

```c
kernel<<< dim3(128,128), dim3(32,32) >>>(...);
             ↑ 派 128×128 个班组     ↑ 每班组 32×32 = 1024 个工人
```

每个线程身上带着 4 个"身份证字段"，随时能查"我是哪班的、班内哪个位子"：

| 字段 | 意思 | 本程序的值 |
|---|---|---|
| `gridDim` | 整个网格"横几块、竖几块" | (128, 128) |
| `blockIdx` | **我所在的班组**横第几、竖第几 | 各自 0~127 |
| `blockDim` | 一个班组横几人、竖几人 | (32, 32) |
| `threadIdx` | 我在班组里横第几、竖第几 | 各自 0~31 |

⚠ `.x` 是"横"、`.y` 是"竖"——用数学坐标系的直觉记：x 横轴、y 竖轴。第三个维度 `.z` 也存在，本程序没用（值恒为 0 / 1）。

### 5.3 把 128×128 个班组"摆"出来看

```
                 blockIdx.x →（横向，列块号）
                  0        1        2      ...      127
              ┌────────┬────────┬────────┬─────┬────────┐
 blockIdx.y  0│ (0,0)  │ (1,0)  │ (2,0)  │ ... │(127,0) │
 （纵向，      ├────────┼────────┼────────┼─────┼────────┤
  行块号）    1│ (0,1)  │ (1,1)  │ (2,1)  │ ... │(127,1) │
     ↓        ├────────┼────────┼────────┼─────┼────────┤
             ...        ...      ...     ...     ...
              ├────────┼────────┼────────┼─────┼────────┤
            127│(0,127) │(1,127) │(2,127) │ ... │(127,127)│
              └────────┴────────┴────────┴─────┴────────┘

  每个格子（例如 (2,1)）= 一个 32×32 的班组
  = 负责原表 in 的「第 1 行块、第 2 列块」那一小块数据
```

两个关键点：

1. `blockIdx.x` 的取值范围是 `0 ~ gridDim.x-1`（0~127），**它是"块"的编号，不是格子的编号**；格子编号要用 5.4 的公式拼出来。
2. 文件里的缩写 `(bx, by)` 就是 `(blockIdx.x, blockIdx.y)`。

### 5.4 拼出"我负责哪个格子"：公式拆解

```c
int i = blockIdx.y * blockDim.y + threadIdx.y;   // in 的行号
int j = blockIdx.x * blockDim.x + threadIdx.x;   // in 的列号
```

像写外卖地址一样，三段相加：

```
i（第几行） =  blockIdx.y    ×  blockDim.y    +  threadIdx.y
               ────────       ──────────        ──────────
               所在"行块"      每块有多少行       我在块内第几行
              （几号宿舍楼）    （楼高几层）       （住几层）
```

具体例子：`in[100][200]`（第 100 行、第 200 列）是谁负责的？

```
行 100：100 ÷ 32 = 3 余 4 → blockIdx.y = 3，threadIdx.y = 4
列 200：200 ÷ 32 = 6 余 8 → blockIdx.x = 6，threadIdx.x = 8
代入验证：i = 3×32+4 = 100 ✓   j = 6×32+8 = 200 ✓
→ 是班组 (bx=6, by=3) 的 thread (tx=8, ty=4)
  他读 in[100*4096+200]，写 out[200*4096+100]
```

### 5.5 和矩阵"行列"的对应：一句口诀

> **x 管"列"，y 管"行"；行号从 `.y` 里来，列号从 `.x` 里来。**

```c
int i = blockIdx.y * ... + threadIdx.y;   // 行号 ← 全是 y
int j = blockIdx.x * ... + threadIdx.x;   // 列号 ← 全是 x
```

所以 `(bx=6, by=3)` 班组负责的是：原表第 3 行块（第 96~127 行）、第 6 列块（第 192~223 列）那个 32×32 小块。

如果表格是长方形 M×N（GEMM 会遇到），网格就是 `grid = (N/32, M/32)`——x 方向跟"列数"走，y 方向跟"行数"走；方阵只是恰好两者相等。

### 5.6 三个容易踩的坑

1. **别把 `.x` 记成"行"。** 出错时的典型症状：小矩阵全 PASS、大矩阵一塌糊涂；方阵的某些写法甚至永远看不出错（谁干哪格换了，覆盖的仍是同一批格子）。别拿"跑通了"当证据，默念"x 横、y 竖"。
2. **只有一维网格时 `.y` 恒为 0。** 若启动写成 `grid(128)`，`blockIdx.y` 永远为 0，所有 `.y` 寻址都会塌掉。本程序明确写 `dim3 grid(128, 128)`，所以 `.y` 才有效。
3. **`.x` 变化最快。** 二维坐标压成线性编号是 `blockIdx.y * gridDim.x + blockIdx.x`；块内线程同理是 `threadIdx.y * blockDim.x + threadIdx.x`。这也是"一个 warp = 同一行、tx 从 0 到 31"的由来。

### 5.7 回头看 V2 的"换角色"

转置的本质是行列对调，"编号系统"也要整体对调：

| | 阶段 1（读 in，抄白板） | 阶段 2（从白板取，写 out） |
|---|---|---|
| 班组横编号 | `blockIdx.x` = 原表**列**块 | 变成 out 的**行**块（out 行 = in 列） |
| 班组竖编号 | `blockIdx.y` = 原表**行**块 | 变成 out 的**列**块 |
| 工人的 tx | 管原表**列** | 管 out 的**列**（取值改拿 `tile[tx][ty]`） |

```c
// 阶段 2 的代码，现在再看：
x = blockIdx.y * TILE_DIM + tx;   // out 的列号 ← 竖编号 + tx
y = blockIdx.x * TILE_DIM + ty;   // out 的行号 ← 横编号 + ty
```

转置嘛，横的就是竖的、竖的就是横的——这就是那三行"看不明白"的来龙去脉。

### 5.8 30 秒自测

W=4096、TILE_DIM=32，班组 `(blockIdx.x=5, blockIdx.y=2)`、工人 `(threadIdx.x=1, threadIdx.y=31)`：

1. 他负责 in 的第几行、第几列？
2. V1 里他读写的是哪两个内存地址？

答案：行 `i = 2×32+31 = 95`，列 `j = 5×32+1 = 161`；读 `in[95*4096+161]`、写 `out[161*4096+95]`（95 和 161 恰好换了个位置）。

## 6. 附录 B：`W` 是什么

**W 就是那张大表格的边长**：表格有 W 行、W 列（方阵）。W 是 Width（宽度）的缩写。

```
W = 4096 时：

        ←────────── W = 4096 列 ──────────→
       ┌──────────────────────────────────┐
  W =  │                                  │
 4096  │       4096 × 4096 的表格          │
  行   │       = 16,777,216 个格子        │
       │       × 4 字节/格 = 64 MiB        │
       └──────────────────────────────────┘
```

### 6.1 从哪里来

```c
int W = (argc > 1) ? atoi(argv[1]) : 4096;
```

命令行给的第 1 个参数就是 W，不给就默认 4096：

```bash
./build/bin/transpose 4096    # W = 4096
./build/bin/transpose 4097    # W = 4097（边界测试：非 32 的倍数）
./build/bin/transpose 1024    # W = 1024（L2 测试：两阵 8 MiB 塞进 L2）
```

### 6.2 为什么除出来是 128

一个班组干活范围只有 32×32，盖不满整张表，所以要铺很多班组：

```
横向：4096 格 ÷ 每块 32 格 = 128 块
纵向：4096 格 ÷ 每块 32 格 = 128 块

代码里（整数除法"向上取整"的经典写法）：
    dim3 grid((W + TILE_DIM - 1) / TILE_DIM, ...);
```

### 6.3 别混淆的两个尺寸

| 名字 | 是什么 | 值 | 谁定的 |
|---|---|---|---|
| **W** | 大表格边长（横 4096、竖 4096） | 4096 | 命令行传入 |
| **TILE_DIM** | 一个班组负责的小块边长 | 32 | 代码写死 |
| **W ÷ TILE_DIM** | 每个方向要几个班组 | 128 | 算出来 |

### 6.4 W 的第二个身份：地址换算的"步长"

```c
in[y * W + x]   // 为什么是 y*W+x？因为「一行有 W 个格子」
```

```
找"第 y 行第 x 列"：先跳过完整的 y 行（每行 W 格）→ 跳过 y×W 格 → 再走 x 格

内存带子:  [第0行的 W 个格] [第1行的 W 个格] [第2行的 W 个格] ...
                 ↑ 跳 1 行 = 跨 W 格
```

所以 W 同时扮演"边长"和"一行有多长"两个角色，方阵里恰好是同一个数。

### 6.5 回头看三次运行

| 命令 | W | 表格大小 | grid | 说明 |
|---|---|---|---|---|
| `transpose 4096` | 4096 | 64 MiB/阵 | (128, 128) | 4096÷32=128 |
| `transpose 4097` | 4097 | 64 MiB/阵 | (129, 129) | 除不尽 → 向上取整；边缘靠 `if (x < W && y < W)` 拦截 |
| `transpose 1024` | 1024 | 4 MiB/阵 | (32, 32) | 1024÷32=32 |

## 7. 附录 C：底层原理答疑（寄存器 / 共享内存 / 取数过程 / "+1"）

> 学习答疑整理（2026-10-13）。四个问题串起来正好是"GPU 的内存世界地图"。

### 7.1 先看地图：数据能待的五个地方

| 存储 | 在哪 | 容量（本机） | 速度（大概延迟） | 谁能用 |
|---|---|---|---|---|
| **寄存器** | SM 内部，工人手边 | 每线程几十个 | 最快（~1 周期） | **每个线程独享** |
| **共享内存** | SM 内部（SRAM） | 每 block 几十 KiB；每 SM 共 ~100 KiB | 快（~20 周期） | **每个 block 独享** |
| L1 缓存 | SM 内部（和共享内存**是同一块 SRAM**） | — | 快 | 自动的，不用你管 |
| L2 缓存 | 芯片上 | 24 MiB | 中 | 全 GPU 共享 |
| **全局内存（DRAM）** | 显存颗粒 | 8 GB | 慢（几百周期） | 全 GPU 共享 |

一句话分层：**离工人越近越小越快越私有，越远越大越慢越共享。** 三个算子的区别，本质就是"数据在这张地图上走了哪条路"。

### 7.2 V1 的存储位置是寄存器吗？

**矩阵本身在全局内存（DRAM）里，从头到尾没动窝；寄存器只是数据"路过"时工人手上的临时位置。**

```
V1 每个线程的一生:
  全局内存 in[i][j] ──读出──> 寄存器(停几个周期) ──写入──> 全局内存 out[j][i]
                                  ↑ 只是"路过"，不是"仓储"
```

- `int i, j` 这两个变量（坐标）确实住在寄存器里——但那是"账本"，不是"货物"。
- 真正的货物（浮点数）也经过寄存器（编译后就是 load → store），但它只在手上停几纳秒，**没有任何数据被"存"在片上**。
- 为什么不能把矩阵搬进寄存器？寄存器每线程私有、只有几十个，而整个矩阵 64 MiB——差了六个数量级。**64 MiB 只能待在仓库（DRAM）里，片上只放得起"过手"的东西。**

所以 V1 的特点：**没有中转站**。慢不是因为"搬得多"，而是因为"路线歪"（写的时候一队人散成 32 个方向）。

### 7.3 V2 的共享内存只有 32×32，怎么盖住 4096×4096？

**对——每个 block 都有自己的私有共享内存；而且它不是"一起算"，是"切成 16384 个小问题，分波算"。**

#### ① 每个 block 一块白板

`__shared__ float tile[32][32]` 这行只写了一次，但硬件是**按正在运行的 block 逐个分配**的：谁上场，就给谁发一块白板；block 退休，白板立刻转给下一个 block。同一时刻存在的白板数量 = 正在运行的 block 数量（本机约 24 块），不是 16384 块。

#### ② 为什么能切开？因为块与块互不依赖

转置有个关键数学事实：**out 的第 (by, bx) 块 32×32，只由 in 的第 (bx, by) 块决定**——把那一块转过来就完事，不需要看别的块一眼。所以 4096×4096 被切成 128×128 = 16384 个独立的小转置。

#### ③ 怎么"一起"？其实是分波（wave）

```
16384 个 block        GPU 只有 24 个 SM，每个 SM 同时装 1 个这种 block
                  ） （本 kernel 一个 block 1024 线程，SM 上限 1536 线程）

     第 1 波:  24 个 block 上场（各抱一块白板）
     第 2 波:  再来 24 个 …… 共约 683 波
```

类比：工厂只有 24 张工作台，接到 16384 个订单（每单 = 一块 32×32）。订单排着队上台，**每张台上摊一块白板，台与台之间互不相干**。所以"整个矩阵一起算"是错觉——**是 16384 个独立小任务在 24 个工位上流水完成**。

（这也是为什么 `__syncthreads()` 只需要在 block 内部同步：跨 block 本来就没依赖。）

### 7.4 "取数"从底层到底发生了什么？（一次"取件"的全程录像）

跟着一队 32 人（一个 warp）走一遍 V2 的一个循环：

```
① 发起读 in 的一块:
   32 人的地址 = 连续的 32 个格子 = 128 B = 正好 1 条 cache line
   └─ 硬件(L1TEX)把它们"拼成一批" → 1 次事务
   DRAM 仓库 ──128B──> L2 分拣 ──> L1 料架 ──> 32 个寄存器（每人手里 1 个数）

② 写白板: tile[ty][tx] = 手上那个数
   32 人手往白板上放 → 地址连续 → 无冲突，唰一下全放好
   （数据从寄存器搬进了 SM 内部那块 SRAM）

③ __syncthreads(): 全班到齐，才开始下一步

④ 从白板取: 读 tile[tx][ty]
   ← ★ 就是这里排队！32 个人同时伸手，抽到什么抽屉由地址决定（见 7.5）

⑤ 写回仓库: out[y*W+x] = 手上新拿到的数
   32 人地址连续 → 又拼成 1 批 → L2 ──> DRAM
```

底层直觉就两句话：

1. **仓库很远很窄**（DRAM 延迟几百周期），所以尽可能"整批搬"（合并访问 = 一车拉 128 B）"少跑腿"（数据复用）；
2. **手边很近很小**（寄存器/共享内存），所以要把反复要用的东西"挪到操作台上"。

**为什么非要有白板？——交换论**（这是最底层的一条逻辑链）：

```
要想"写得快"，一队 32 人写的地址必须连续（这是硬件规矩）；
out 里连续的 32 格，每格的值来自 in 里"竖着的一列"；
——也就是说，这 32 个值分散在 32 个不同工人手里（每人一个）。
要让他们各就各位，工人们必须"互相换货"。
但寄存器是私有的，工人之间互相看不见 → 必须有个公共区域来交换。
这个公共区域，就是共享内存（白板）。
```

V1 不需要交换（各搬各的），所以它根本没用共享内存——但代价就是写得慢。**"用白板"不是炫技，是"想两头都快"逼出来的必然结果。**

### 7.5 V3 的"+1"为什么立刻见效？

#### 共享内存的物理结构

白板不是一整块，是**32 个抽屉（bank，编号 0~31）并排**。硬件规矩：

- 一队 32 人同时伸手：**每人一个抽屉 → 1 拍全部拿到**；
- **几个人挤同一个抽屉 → 排队**（挤 n 个就排 n 拍）；
- 一个格子属于哪个抽屉：**格子编号 mod 32**（格子编号 = 行×行宽 + 列）。

#### V2 的倒霉巧合

阶段 2 从白板"竖着取"：一队 32 人拿的是**同一列**（tx 变、ty 固定）：

```
行宽 32：格子编号 = tx×32 + ty
         对 32 取余 = ty          ← 与 tx 无关！
         → 32 个人全伸进 ty 号抽屉 → 排队 32 拍 🐌
```

这一刻的代价：**每人取一次数，都要等 32 拍**。而这个过程每个元素都要发生一次（1600 万次），累积起来就是把 V2 拖慢的那只手。

#### V3 的"+1"做了什么

行宽改成 33 后：

```
格子编号 = tx×33 + ty
对 32 取余 = (tx×33 + ty) mod 32
          = (tx×1 + ty) mod 32      ← 因为 33 = 32+1，乘 33 取余等于乘 1
          = (tx + ty) mod 32
         → tx = 0..31 时余数走遍 0,1,2,...,31 → 一人一个抽屉 ✅
```

直观图像：原来 32 个人排成一列纵队、手全伸向同一个格子；把每行多垫一格，等于**把队伍斜过来**——每个人的手正好落在不同抽屉上（像棋盘对角线）。

**为什么"立刻"就快？** ① 代价极小——每行多一个空座，总共多 128 B；② 收益极大——那条最频繁的指令从"32 拍"变回"1 拍"；③ 无副作用——其他代码一个字都不用改。

**为什么整体只快 1.3~1.8 倍、不是 32 倍？** 因为 bank conflict 只是流水线里的一段（收费站），不是全程。取消收费站，全程时间只减掉"它占的那一段"；剩下的路程（DRAM 带宽、其他指令）还是原来的样子。数据也印证：DRAM 规模下 1.3~1.4x，L2 规模下（DRAM 不再拖后腿）拉大到 1.8x。

**延伸小知识**：为什么加 1 行、加 2 不行？因为要看"步长 34 与 32 的最大公约数"：gcd(34,32)=2 → 余数只能取到 16 个值 → 变成 16 路冲突。**加 1 恰好让"新步长与 32 互素"，才能 32 人各占一个抽屉。**

### 7.6 三条数据流，一张图收尾

```
V1:  DRAM ──(读合并)──> 寄存器 ──(写散开)──> DRAM          → 慢在"写"
V2:  DRAM ──(读合并)──> 寄存器 ──> 白板 ──> 排队取数 ──> 寄存器 ──(写合并)──> DRAM   → 慢在"取数排队"
V3:  同 V2，但白板取数不排队                              → 两头的路都顺了
```

记三句话：

1. 数据平时住仓库（DRAM），寄存器只是过手的地方；
2. 每个 block 抱着自己的小白板，大矩阵靠"无数个独立小块分波算"；
3. 白板值钱就值钱在"交换"二字，而 +1 是给交换修的那条斜向通道。

## 8. 附录 D：跨步访问的"搬家论"（对一句直觉的修正）

> 学习答疑整理（2026-10-14）。起因是一句自己的总结——"从共享内存转置写出 DRAM 也是跳着取址，只是共享内存快所以加速了"。这句话**对了一半**，修正三处后，整张搬运地图才算真正打通。

### 8.1 纠正一：写给 DRAM 那一步不是跳着的，是连续的

把阶段 2 拆成两次独立访问看：

```
阶段 2 的两次访问：

  读共享内存：tile[tx][ty]   → ← 只有这一步"跳着取"！（地址步长 32 或 33 个字）
  写 DRAM：   out[y*W + x]   → 完全连续（同队 tx 从 0 到 31 → 地址 +1）✓

对比阶段 1 的两次访问（两次都是连续的）：

  读 DRAM：   in[y*W + x]    → 完全连续 ✓
  写共享内存：tile[ty][tx]   → 完全连续 ✓
```

**全程只有一处跨步访问，而且它被"关"在共享内存里面。** DRAM 那头的读和写两次都是 128 B 一条线的完美连续——这正是 tiling 的全部目的。（"从共享内存转置写出 DRAM 也是跳着取的"不成立：跳出 DRAM 的恰恰是被消灭了。）

### 8.2 纠正二：加速的本质不只是"共享内存快"

正确的逻辑链：

> **转置天生逃不掉一处跨步访问**（见第 1 步的证明：横竖垂直）。
> 你能做的不是"消灭"它，而是"搬家"——
> - V1：跨步发生在 **DRAM 写** → 代价最贵；
> - V2：跨步搬到 **共享内存读** → 便宜一大截；
> - V3：同样的跨步，stride 改成 33 让 bank 不撞 → 代价几乎归零。

就算共享内存和 DRAM 一样快，"把跨步搬到片上"本身也是赚的——因为两种内存**罚的东西根本不是一回事**：

| | 跨步访问的惩罚形式 | 后果 |
|---|---|---|
| **DRAM** | **浪费流量**：32 个 4 B 散写 → 动用 32 个 32 B sector（搬 1024 B、有效的只有 128 B） | 有效带宽打到 ~1/8，还占着全 GPU 共享的带宽 |
| **共享内存** | **排队**：32 个人挤同一个 bank → 指令串行 32 拍 | 字节一个不浪费；损失的是片上流水线时间 |

一个罚"钱"（流量），一个罚"时间"（周期），单位完全不同。把跨步从 DRAM 挪到片上，等于**用便宜的"时间罚单"换掉昂贵的"流量罚单"**——而且这张时间罚单还能用 +1 继续打折（V2 → V3 的 1.35x）。

### 8.3 纠正三：共享内存不罚"跨步"，只罚"撞 bank"

注意 V3 的读**依然是跨步的**（stride 33 个字，不是 1）——但它毫无代价。为什么？

- 共享内存判断好坏，看的是 **地址 mod 32 有没有撞车**，不看连续不连续；
- 步长 1、3、33 都可以零冲突；步长 32、64（撞到同一余数）才是灾难；
- 而 DRAM 判断好坏，看的就是**连续不连续**——步长 33 在 DRAM 里照样是灾难。

所以"跳着取"这个描述：对 DRAM 是罪状，对共享内存只是措辞——**在共享内存里，跳得好反而没事**。

### 8.4 修正版表述与"搬家论"

> "转置时确实还残留一处'跳着取数'，但它只发生在**共享内存内部**（阶段 2 的 `tile[tx][ty]`）；写给 DRAM 是完全连续的。加速的本质不是'共享内存恰好快'，而是**把不可避免的跨步访问从 DRAM 搬到了片上**：DRAM 只看到连续读 + 连续写，跨步的代价改由片上'排队'来付——而这个代价还能用 padding 再压到接近零。"

**一句话总纲：转置的跨步消灭不了，但可以搬家——从最贵的 DRAM 搬进片上，再在片上把它调成免费。**

这句就是后面 GEMM 优化的总纲：GEMM 里 A/B 两个 tile 的搬运、寄存器分块，玩的都是同一个"搬家"游戏。
