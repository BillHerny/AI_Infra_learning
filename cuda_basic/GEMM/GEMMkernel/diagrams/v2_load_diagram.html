GEMMkernel_v2_smem：两条载入语句的数据流

以 2048×2048×2048、block(32×32)、block(bx=0, by=1)、kt=0 为例。一个格子 = 一个 float。

约定 block(bx, by) = blockIdx(x, y)；thread(tx, ty) = threadIdx(x, y)
坐标 i = blockIdx.y·blockDim.y + threadIdx.y = by·32 + ty  →  C 的行
坐标 j = blockIdx.x·blockDim.x + threadIdx.x = bx·32 + tx  →  C 的列
举例 block(bx=0, by=1) 的 thread(tx=5, ty=3)：
i = 1·32 + 3 = 35    j = 0·32 + 5 = 5  →  负责 C[35][5]
by=1 表示从第 32 行开始的那一条「行带」，带内再走 ty=3 行 → 第 35 行
bx=0 表示第 0 条「列带」（第 0..31 列），带内再走 tx=5 列 → 第 5 列

图 1 ｜ 一个 block 认领 C 的 32×32 小块，一条 warp 就是一整行

因为 blockDim.x == 32，warp 内 tx = 0..31 填满、ty 固定 —— 这条性质后面所有合并访问都靠它。

← tx = 0tx = 31 →（即 j = col0 + tx）

图 2 ｜ 载入 A 片：As[ty][tx] = m1[i*K + kt + tx]

warp 内 tx 走的是 k 方向，ty 定死了 A 的哪一行。

row i = row0+ty = 35
row i+1
这一段就是 m1 + i*K + kt 开始的 32 个连续 float。深蓝 32 格 = warp(ty=3) 的 32 个 lane 各自搬的那 1 个： lane tx 搬第 tx 格。
它上面 / 下面的两行（浅蓝）不是这个 warp 的活，由 ty=2 / ty=4 的 warp 负责。
同一条 warp 指令（LDG.32）里 32 个 lane 的地址：
lane tx :  0     1     2    ...   31
地址     : m1[i*K+kt+0] ... m1[i*K+kt+31]      ← 32 个连续 float
         └──────────── 128 B = 1 次合并事务 ────────────┘
所以「一次取出 32 个 float」不是单个线程的能力，而是 32 个线程合力 + 硬件合并： 每条 LDG.32 只搬 4 B，但 32 个 lane 的地址连续 → 硬件合成 1 次 128 B 事务。
warp(ty=3) 搬完 → 写出 As 的第 3 行
⤴
32 条 warp（ty = 0..31）各搬一行
→ 拼满整片 As[32][32] = 1024 个数 = 4 KB
而且写入坐标就是读取坐标，没有转置：
As[ty][tx] ← A[row0+ty][kt+tx]

图 3 ｜ 载入 B 片：Bs[ty][tx] = m2[(kt + ty)*N + j]

这里 ty 变的是 k 方向，tx 走的是列 j 方向 —— 跟 A 那次正好互换，但「一条 warp 搬一整行」的结构完全一样。

row kt+ty−1
row kt+ty = 3
row kt+ty+1
这一段就是 m2 + (kt+ty)*N + col0 开始的 32 个连续 float（B 的第 3 行、第 col0..col0+31 列）。
深橙 32 格 = warp(ty=3) 的 32 个 lane 各自搬的那 1 个：lane tx 搬第 tx 格。 
lane tx :  0            1          ...            31
地址     : m2[(kt+ty)*N + col0 + 0] ... m2[(kt+ty)*N + col0 + 31]
           └──────── 同一个 k（行固定）────────┘
           32 个连续 float → 128 B 1 次合并
关键：载入阶段根本没有线程去「取 B 的一列」。
每个线程只负责 B 片里的一格 (row = kt+ty, col = col0+tx)；
而某个线程计算时需要的那一列（32 个不同 k），是后来在 smem 里被拼出来的 —— 见 图 4。
warp(ty=3) 搬完 → 写出 Bs 的第 3 行
⤴
32 条 warp（ty = 0..31，各自对应一个 k）各搬一行
→ 拼满整片 Bs[32][32] = 4 KB
同样没有转置：
Bs[ty][tx] ← B[kt+ty][col0+tx]

图 3b ｜ thread(tx=5) 需要的那一列，是谁搬来的？

列 tx = 5 的 32 个格子，来自 32 条不同的 warp（ty = 0..31），共同点是它们都用了 tx = 5 这条 lane。

竖着那一列（深橙）= Bs[0..31][5]
= B[kt+0..kt+31][col0+5] = 计算时 thread(tx=5) 要用的 32 个数
∙ Bs[0][5] ← warp ty=0 的 lane tx=5
∙ Bs[1][5] ← warp ty=1 的 lane tx=5
∙ …
∙ Bs[31][5] ← warp ty=31 的 lane tx=5
每个 warp 提供的都是「一行里连续 32 格」中的一格，
所以合并性一点没损失，列却被凑齐了。

图 4 ｜ 计算阶段：列式的读取发生在 smem，不在 DRAM

acc += As[ty][k] * Bs[k][tx]（k = 0..31）。同一时刻（固定 k）看 warp 内 32 个 lane 读什么：

A：32 个 lane 读同一格 → 广播
As[ty][k]：warp 内 ty 固定、k 固定 → 1 个地址，硬件广播给 32 个 lane，1 个事务
B：32 个 lane 读连续一整行 → 无冲突
Bs[k][tx]：k 固定、tx = 0..31 → 地址 k*32 + 0..31 → 32 个不同 bank，零冲突
「一个线程要读 B 的一列」并不慢，因为你算的账算错了维度。
bank / 合并这些开销是按指令算的，不是按「某个线程随时间走的路」算的：
  • 固定 k 的那一条 LDS，warp 内读的是连续 32 格 → 1 个 wavefront，完美；
  • k 从 0 变到 31，只是下一条指令换到下一行 —— 每条指令都各自完美。
真正会吃亏的是「同一条指令里地址跨 cache line」，那发生在 global，不发生在 smem。

图 5 ｜ 反例：如果硬要让 tx 去走 k 方向

假设写成 Bs[tx][ty] = m2[(kt + tx)*N + col0 + ty]，warp 内 tx 变成 k → 地址步长变成 N 个字。

lane tx :   0        1        2      ...     31
地址     : row kt  row kt+1 row kt+2  ...  row kt+31     ← 每个 lane 落在不同的 cache line
           │        │        │               │
           └ 32 次独立的 32 B sector 请求，每次只用 4 B ┘
           有效字节 128 B / 实际搬运 1024 B = 效率 12.5%
这才是「行主序导致取列取不动」的真正症状 —— 而 V2 通过「重新分工谁搬哪一格」把它绕开了： 搬运按行（合并友好），消费按列（bank 友好），中间的转换交给 smem。

是否转置否否

「取列」发生在哪都在计算段的 smem 读取：As[ty][k] 广播、Bs[k][tx] 连续，均无冲突
一句话：DRAM 只知道线性地址 —— 「行主序」是你用 k*N + j 这个下标表达式赋予它的含义。 两条语句都刻意让 tx（warp 内连续变化的那一维）去走矩阵的行内方向， 于是搬运阶段 100% 合并；需要的那一列由 32 条 warp 在 smem 里拼出来，转置是白拿的。
