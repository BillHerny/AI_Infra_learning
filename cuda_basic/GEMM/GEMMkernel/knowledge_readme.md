## 1. 硬件课：GPU 里到底有什么

### 1.1 车间（SM）

把 GPU 想成一个工厂：

- 这块显卡有 **24 个车间**（SM，Streaming Multiprocessor）。
- 每个车间有 **128 个工人**（FP32 计算核心）。
- 每个工人每个时钟能做 **1 次乘加**（FMA：`a*b+c`，算 2 次浮点运算）。
- 车间时钟大约 **2.6 GHz**（每秒 26 亿拍）。

所以整块 GPU 的算力上限是：

```
24 车间 × 128 工人 × 2 次运算 × 2.6e9 拍/秒 ≈ 16 万亿次/秒 = 16 TFLOPS
```

这就是「FP32 峰值 16 TFLOPS」的来历。**任何 kernel 都不可能超过它。**

### 1.2 班组（warp）

GPU 真正调度时，不是一个人一个人地派活，而是 **32 个人一组**，叫一个 **warp**。

- 一个 warp 的 32 个人（lane）**同时执行同一条指令**（SIMT）。
- 一个 256 线程的线程块（block）= 8 个 warp。
- 关键：当某个 warp 在等内存时，车间可以立刻换另一个 warp 来干活。这叫 **隐藏延迟**。

所以「同时有多少个 warp 可切换」非常重要，这个比例叫 **占用率（occupancy）**。

### 1.3 存储金字塔

数据放在离工人越近的地方，取得越快，但容量越小：

| 层级 | 类比 | 容量 | 速度（本机估算） |
|---|---|---|---|
| 寄存器 | 工人自己手里的工具 | 每人几十~两百个 | 最快，几乎不花时间 |
| 共享内存 smem | 车间中央的共享工作台 | 每车间约 100 KB | 全 GPU 约 8 TB/s |
| L1 缓存 | 车间门口的小货架 | 和 smem 共用约 128 KB/车间 | 约 8 TB/s |
| L2 缓存 | 整层楼的仓库 | 24 MiB（全 GPU 共享） | 几 TB/s |
| 显存 DRAM | 厂区外的大仓库 | 8 GB | **256 GB/s** |

- 大仓库（DRAM）容量大，但速度只有工作台的 **1/30**。
- 所以优化的核心永远是：**让数据在工作台/手里被反复使用，少跑大仓库。**

> 补充：共享内存有 **32 个格子（bank）**，每个 4 字节。32 个人同时伸手，如果每个人要的格子都不同，一拍就能拿完；如果两个人要**同一个格子里的不同东西**，就得排队——这就是后面反复出现的 **bank conflict（银行冲突）**。

### 1.4 三个重要的「体检指标」

**① 算术强度 AI**

\[
AI = \frac{\text{做了多少次浮点运算}}{\text{搬了多少字节}}
\]

AI 越大，说明这份工作越「计算密集」，越不怕内存慢。方阵 \(N^3\) 时：

\[
AI = \frac{N}{6}
\]

例如 2048³ 的 AI ≈ 341，非常高。

**② 拐点（roofline 分界）**

\[
\text{拐点} = \frac{\text{峰值算力}}{\text{显存带宽}} = \frac{16\text{ TFLOPS}}{256\text{ GB/s}} \approx 62\ \text{flop/B}
\]

- AI > 62 → 计算受限（算力是瓶颈）；
- AI < 62 → 内存受限（带宽是瓶颈）。

2048³ 的 AI=341，远大于 62，所以它**不是被显存带宽卡住的**。

**③ 每 FMA 要读多少字节（B/FMA）**

这是这份读本的主线：

- V1：每次乘加读 2 个数（A 一个、B 一个）→ **8 B/FMA**
- V3：读 8 个数做 16 次乘加 → **2 B/FMA**
- V4：字节数不变，但指令数变少 → **2 B/FMA**
- V5：读 16 个数做 64 次乘加 → **1 B/FMA**

> **一句话记住：优化 GEMM 就是想办法让「每次乘加要搬的字节数」越来越小。**

### 1.5 为什么 GEMM 有得优化？

矩阵乘法：

\[
C[i][j] = \sum_{k} A[i][k] \times B[k][j]
\]

- 一个 \(A[i][k]\)，会被同一行的 **N 个输出**用到；
- 一个 \(B[k][j]\)，会被同一列的 **M 个输出**用到。

也就是说，**数据天然具有大量复用**。所有版本的区别只有一句话：

> **这些被复用的数，放在哪里（寄存器 / smem / L1 / DRAM），以及一次拿多少个。**

## 2. V1：最直白的写法

### 2.1 它做了什么

每个线程负责 C 的一个格子：

```cuda
i = 本线程负责的行
j = 本线程负责的列
acc = 0
for k in 0..K-1:
    acc += A[i][k] * B[k][j]
C[i][j] = acc
```

用菜来打比方：**一个厨师做一道菜，每做一步都去仓库拿两样原料。**

### 2.2 账本

- 每个输出要做 K 次乘加；
- 每次乘加读 2 个数（4 B + 4 B）；
- 所以 **8 B/FMA**。

2048³ 时：

- 乘加总数 = 2048³ ≈ 8.59 × 10⁹ 次；
- 操作数读取 = 2 × 8.59e9 次 × 4 B ≈ **68.7 GB**；
- 实测 17.288 ms → 相当于每秒喂 **3.97 TB/s**。

### 2.3 为什么 V1 还能跑到约 1 TFLOPS？

因为它有硬件帮忙：

- `A[i][k]` 在一个 warp 里是**同一个地址**——32 个人要同一份数据，硬件一次就够（广播）；
- `B[k][j]` 是连续地址——一次 128 B 全用上（合并访问）；
- **L1 缓存**把重复读接住了，所以 68.7 GB 的需求并没有全打到 DRAM。

真正打到显存的，只有每个 block 的 A/B 小片，大约 2 GB，折合 124 GB/s——连 256 GB/s 的一半都不到。

### 2.4 那它到底卡在哪？

68.7 GB ÷ 17.3 ms = **3.97 TB/s**，而 L1 的聚合带宽大约 **8 TB/s**——V1 已经用掉一半左右。

- 它没卡在显存带宽（AI=341，DRAM 下限只占实测的 1.1%）；
- 它卡在 **L1 的供给速度 + 每次只能做 1 个乘加的指令效率**。

> **一句话记住：V1 不傻，它把「重复读」交给了硬件缓存；但每个线程只算 1 个数，天花板很低。**

## 3. V2：加了共享内存，为什么反而更慢？

### 3.1 想法

教科书常说：把 A、B 的小块（tile）先搬进共享内存，块内复用，能省全局读。

V2 就是这么做的：

- 32×32 的线程块，认领 C 的 32×32 小块；
- 把 A 的 32×K 和 B 的 K×32 分 32 段搬进 smem；
- 每段搬完同步一次，再算。

### 3.2 结果：20.36 ms，比 V1 慢 15%

原因有三条：

1. **读取次数没变**：每个线程还是只算 1 个格子，每次乘加仍要读 2 个数。smem 只是把「从 L1 读」换成「从 smem 读」。
2. **多了一趟搬运**：global → 寄存器 → smem，多写一遍。
3. **同步很贵**：一个 1024 线程的块，每段要 2 次全块同步；而每 SM 只能放 1 个这样的块，同步时整个车间停摆，没有别的块来填空。

### 3.3 为什么教科书里 V2 能快 3~8 倍？

- 老 GPU 的 L1 **不缓存 global 数据**（或者很小），naive 版真的在打显存；
- 那些教程的 tiling 通常还叠加了**寄存器分块**（一个线程算多个输出），收益大头在那里；
- 现代 GPU（Volta 起）L1 又大又能缓存 global，naive 版的重复读已经被硬件接住了。

> **一句话记住：换个更快的仓库，不等于少跑几趟。V2 砍对了病，但现代 GPU 上这个病已经不存在了。**

## 4. V3：一个线程算 16 个输出（第一次质变）

### 4.1 先算一笔小账：16 个输出到底要读多少个数？

固定一个 k，只看 4×4 = 16 个输出：

- **V1/V2 的做法**：16 个线程各算一个输出，每人读 2 个数 → 16 × 2 = **32 次读取**。
- **V3 的做法**：1 个线程算这 16 个输出，只需要读 A 的 4 行 + B 的 4 列 = **8 次读取**。

同样做完 16 次乘加，读取次数从 32 降到 8——**÷4**。

```
V1/V2：16 个输出 = 16 个线程 × 每人读 2 个数 = 32 次
V3   ：16 个输出 = 1 个线程 × 读 4+4 个数   = 8 次
```

### 4.2 这 8 个数怎么变成 16 次乘加？

因为 A 的每个数要和 B 的每个数都乘一次（两两组合）：

```
          b0    b1    b2    b3
       ┌─────┬─────┬─────┬─────┐
  a0   │a0b0 │a0b1 │a0b2 │a0b3 │
       ├─────┼─────┼─────┼─────┤
  a1   │a1b0 │a1b1 │a1b2 │a1b3 │
       ├─────┼─────┼─────┼─────┤
  a2   │a2b0 │a2b1 │a2b2 │a2b3 │
       ├─────┼─────┼─────┼─────┤
  a3   │a3b0 │a3b1 │a3b2 │a3b3 │
       └─────┴─────┴─────┴─────┘
```

- `a0..a3` 是 A 的第 `4ty .. 4ty+3` 行、当前 k 列；
- `b0..b3` 是 B 的当前 k 行、第 `4tx .. 4tx+3` 列；
- 表格里每个格子 `a_i × b_j`，分别累加到 `acc[i][j]`。

> 关键点：**同一个 `a0` 会被 b0..b3 用 4 次；同一个 `b0` 会被 a0..a3 用 4 次。** 这就是「读一次、用四次」。

### 4.3 一个线程在 C 上的位置

```
C 的一个 block：64 行 × 64 列
┌──────────────────────────────────────┐
│ 16×16 个 4×4 小方块                    │
│                                        │
│ 线程 (tx, ty) 负责：                    │
│   行 = 4ty .. 4ty+3                    │
│   列 = 4tx .. 4tx+3                    │
└──────────────────────────────────────┘
```

- 线程块是 16×16 = 256 个线程（不是 V2 的 32×32 = 1024）；
- 每个线程 4×4 → 整个块刚好覆盖 C 的 **64×64**；
- 线程坐标 `(tx, ty)` 决定「我负责哪 16 个格子」，与载入时用的线性编号 `tid` 是两回事（`tid` 只用于分工搬数据）。

### 4.4 三级复用：global → smem → 寄存器

以 2048³、一个 block、一个 k 段（BK=16）为例：

| 层级 | 每个 k 段的数量 | 说明 |
|---|---|---|
| global → smem | (64+64)×16 = 2048 个数 = **8 KB** | 每个元素只从显存搬一次 |
| smem → 寄存器 | 256 线程 × 16 个 k × 8 次 = **32768 次读** | 每个全局元素被 16 个线程各读 1 次 |
| 寄存器 → FMA | 64×64×16 = **65536 次乘加** | 每个 smem 读出的值参与 4 次乘加 |

比例是 **1 : 16 : 32**。换成「一个 A 元素的一生」：

```
从显存搬 1 次 → 被 16 个线程各读 1 次 → 每次读参与 4 个乘加 → 共服务 64 次乘加
```

### 4.5 为什么要沿 K 分 16 一段？

- 不能把整个 K 都塞进 smem：64×2048 个 float = 512 KB，远超 smem 容量；
- 所以每 16 个 k 为一段：`BK = 16`；
- 段数 = `ceil(K / 16)`，K=2048 时是 128 段；
- 每一段的节奏都是：**载入 A/B 小块 → 同步 → 用 smem 计算 → 同步 → 下一段**。

### 4.6 成绩与体检

- 2048³：**4.995 ms，3439 GFLOPS**，是 V1 的 **3.46 倍**；
- 每 FMA 读取从 8 B 降到 2 B；
- 全局读从 8 flop/B 升到 16 flop/B（一个 A 元素在块内被 64 个输出复用）；
- 每 SM 能驻 **4 个 block**（1024 线程 / 上限 1536），同步时还有其他 block 在算。

### 4.7 为什么 V3 修了 bank conflict 也只快 2.2%？

V3 原来的 smem 有两个 2-way bank conflict：

- `As[64][16]` 的行 stride 是 16 个字；一个 warp 里 `ty=0/1` 读第 i 行和第 4+i 行，两个地址相差 4×16=64 个字，`64 mod 32 = 0` → 落在同一个 bank；
- `Bs[k][4tx+j]` 的 16 个 lane 步长是 4 个字，只覆盖 8 个 bank、每个被 2 个 lane 用 → 2-way。

修法：`As` 加一列 padding（stride 17），B 改成列交错（`tx + 16j`）。修完后 ncu 实测：

| 指标 | 修前 | 修后 |
|---|---|---|
| bank conflicts | 134,217,728 | **0** |
| wavefronts | 268,455,044 | **134,218,625** |
| 2048³ 用时 | 5.105 ms | **4.995 ms（+2.2%）** |

为什么冲突清零了却几乎不快？因为 V3 现在卡在**指令条数**，不是数据字节数：

- 每个 k 步：**8 条 LDS + 16 条 FFMA**；
- 实测 LSU（发内存指令的管道）每 2 个周期才吃一条指令 → 8 条 LDS 要 **16 周期**；
- 而 16 条 FFMA 只要 **4 周期**（每周期 4 条）；
- 所以 FMA 工人最多只能忙 4/16 = **25%**，上限约 **4 TFLOPS**；实测 3.44，正好贴着。

ncu 也印证：`pipe_lsu = 98.25%`（发指令的管道满了），但共享内存的数据通路只忙了约 **43%**。

> **一句话记住：V3 证明了「减少取数次数」有效；它同时把瓶颈从「搬多少字节」换成了「发多少条指令」。**

## 5. V4：一条指令搬 4 个数（第二次质变）

### 5.1 V3 留下的问题：不是字节多，而是指令多

V3 每个 k 步的指令比例是：

```
8 条 LDS（读 smem） + 16 条 FFMA（乘加） = 24 条指令
```

- FMA：16 条只需要 4 个周期；
- LDS：8 条需要 16 个周期（每 2 周期一条）；
- 工人大部分时间在等内存指令，**数据通路却只忙了 43%**。

所以 V4 的目标不是「少搬字节」，而是**让每条内存指令一次搬更多**。

### 5.2 float4 / LDS.128 是什么？

- 一个 `float` 占 4 字节；`float4` = 4 个 float = **16 字节**；
- 一条 `LDS.128` 指令一次读 16 B，相当于把 4 条 `LDS.32` 合成 1 条；
- 代价：地址必须是 **16 字节的整数倍**（对齐），否则硬件会报错或走慢路径。

```
4 条 LDS.32： [f0] [f1] [f2] [f3]   ← 4 条指令
1 条 LDS.128：[f0 f1 f2 f3]         ← 1 条指令，16 B
```

### 5.3 为了能用 float4，smem 要怎么摆？

**A 要转置存。** 原来 `As[row][k]` 是按行存的，线程要的 4 行地址不连续；改成：

```
As_t[k][row] = A[row0 + row][kt + k]
```

这样 `As_t[k][4ty .. 4ty+3]` 就是连续的 4 个 float，一条 `LDS.128` 就能读走。

**行长度要取 4 的倍数。** `As_t` 的行长从 64 改成 **68**（`BM + 4`）：

- 如果只加 1（65），虽然能避开 bank conflict，但每行字节数 = 260 B，不是 16 B 的倍数 → 某些行会踩到未对齐地址；
- 加 4（68）→ 每行 272 B = 17 × 16 B，任何 `k` 的起点都对齐。

一个具体例子：`k = 3, ty = 2`：

```
字地址 = 3 × 68 + 2×4 = 212
字节地址 = 212 × 4 = 848 = 53 × 16  → 16 B 对齐 ✓
```

### 5.4 每个 k 步、每段的指令数

- 每个线程每 k 步：**2 条 LDS.128（A 一次、B 一次） + 16 条 FFMA**；
- 每段（BK=16）：32 条 LDS.128 + 256 条 FFMA；
- 整个 2048³ kernel：共享内存读指令从 V3 的 **134,217,728 条**降到 **33,554,432 条（÷4）**。

注意：**字节数没变**（仍是 2 B/FMA），减少的只是「指令条数」。

### 5.5 成绩与体检

- 2048³：**2.798 ms，6141 GFLOPS**，是 V3 的 **1.79 倍**、V1 的 **6.18 倍**；
- LSU 管道 98.25% → **59.25%**；FMA 管道 21% → **40.97%**；
- ncu 实测每条 LDS.128 平均 3 个 wavefront（A 是广播、B 是 2 个），冲突为 0。

### 5.6 代价：寄存器涨到 87，占用率掉到 2 块/SM

- 16 个累加器 + 8 个操作数 + 地址/循环变量 → 编译器用了 **87 个寄存器**；
- `65536 ÷ (256 × 87) = 2.94` → 每 SM 只能驻 **2 个 block**（512 线程，占用率 33%）；
- 但即使占用率从 67% 掉到 33%，V4 还是快了 79%——因为原来卡的是**指令条数**，不是占用率。

> **一句话记住：向量化减少的是「指令条数」，不是「字节数」；它正好打中了 V3 的新瓶颈。**

## 6. V5：一个线程算 64 个输出（第三次质变）

### 6.1 从 4×4 到 8×8：再做一次乘法

V4 每线程 4×4：每 k 步 2 条 LDS.128 + 16 条 FFMA（0.125 条/FMA、2 B/FMA）。
V5 每线程 **8×8 = 64 个输出**：

- 每 k 步读 A 的 8 行 + B 的 8 列 = **16 个数**；
- 这 16 个数两两组合 → **64 次乘加**；
- 用 **4 条 LDS.128 + 64 条 FFMA** → **0.0625 条/FMA**、**1 B/FMA**。

用图看就是一张 8×8 的乘法表：

```
              b0  b1  b2  b3  b4  b5  b6  b7
           ┌───┬───┬───┬───┬───┬───┬───┬───┐
     a0    │ × │ × │ × │ × │ × │ × │ × │ × │
     a1    │ × │ × │ × │ × │ × │ × │ × │ × │
     a2    │ × │ × │ × │ × │ × │ × │ × │ × │
     a3    │ × │ × │ × │ × │ × │ × │ × │ × │
     a4    │ × │ × │ × │ × │ × │ × │ × │ × │
     a5    │ × │ × │ × │ × │ × │ × │ × │ × │
     a6    │ × │ × │ × │ × │ × │ × │ × │ × │
     a7    │ × │ × │ × │ × │ × │ × │ × │ × │
           └───┴───┴───┴───┴───┴───┴───┴───┘
           8 行 × 8 列 = 64 个累加器，全部住在寄存器里
```

为什么不再往上做 16×16？因为要 256 个累加器，单个线程的寄存器根本放不下（会溢出到显存，性能断崖）。

### 6.2 块结构与地址

- 线程块仍是 16×16 = **256** 个线程；
- 每线程 8×8 → 整块负责 C 的 **128×128**；
- smem：
  - `As_t[16][132]`：A 转置存，128 行 + 4 列 padding（132 字 = 528 B/行，16 B 的倍数）；
  - `Bs[16][128]`：B 的 16 个 k × 128 列；
  - 合计约 **16.25 KB**；
- 读法：
  - A：`As_t[k][8ty .. 8ty+7]` → **2 条 LDS.128**；
  - B：两段 4 列（`4tx` 与 `64+4tx`）→ **2 条 LDS.128**；
- 写回：每线程 64 个结果，行是 `8ty+i`，列同样分两段。

### 6.3 每个 k 步、每段的账

| 项目 | 每线程每 k 步 | 每线程每段（BK=16） |
|---|---|---|
| 内存指令 | 4 条 LDS.128 | 64 条 |
| 乘加 | 64 条 FFMA | 1024 条 |
| 读写字节 | 16 个 float = 64 B | — |
| B/FMA | **1 B** | — |

整个 2048³ kernel：共享内存读指令 **16,777,216 条**（V4 是 33,554,432，再 ÷2）。

### 6.4 寄存器与占用率：用并行度换效率

- 64 个累加器 + 16 个操作数 + 地址/循环变量 → 编译器用了 **128 个寄存器**；
- `65536 ÷ (256 × 128) = 2` → 每 SM 正好 **2 个 block**（512 线程，16 个 warp，占用率 32%）；
- 好消息：`LOCAL = 0`，没有 spill，64 个累加器全部真的在寄存器里；
- 坏消息：每个 SM 只有 16 个 warp 可切换，藏延迟的能力比 V3（32 个 warp）弱一半。

### 6.5 B 读的 bank conflict：从 4-way 到 0

原版让每个线程连续读 8 列：`Bs[k][tx*8 + {0,4}]`。以 `k=0` 为例，看 16 个 lane 的地址：

| lane (tx) | 字地址 | 落在哪些 bank |
|---|---|---|
| 0 | 0..3 | 0,1,2,3 |
| 1 | 8..11 | 8,9,10,11 |
| 2 | 16..19 | 16,17,18,19 |
| 3 | 24..27 | 24,25,26,27 |
| 4 | 32..35 | **0,1,2,3**（和 lane 0 撞） |
| 5 | 40..43 | **8,9,10,11**（和 lane 1 撞） |
| … | … | … |
| 15 | 120..123 | **24..27**（和 lane 3 撞） |

4 个 lane 共用一组 bank → **4-way bank conflict**。ncu 实测：

| 指标 | 修前 | 修后 |
|---|---|---|
| bank conflicts | 33,554,432 | **0** |
| wavefronts | 83,889,120（5/指令） | **50,333,884（3/指令）** |
| 2048³ 用时 | 2.124 ms | **2.032 ms（+4.5%）** |

修法：把 8 列拆成两段 4 列——前 64 列一段、后 64 列一段：

```cuda
// 原版：lane 步长 8 字 → 4-way conflict
// b0 = Bs[k][tx * 8 + 0];
// b1 = Bs[k][tx * 8 + 4];
// 修正：lane 步长 4 字（16 B）
b0 = Bs[k][4*tx + 0];        // 列 4tx .. 4tx+3
b1 = Bs[k][64 + 4*tx + 0];   // 列 64+4tx .. 64+4tx+3
```

注意：**写回的列映射必须同步改**，否则结果会对不上：

```cuda
int col = col0 + (j < 4 ? 4*tx + j : 64 + 4*tx + (j - 4));
```

### 6.6 成绩

| 形状 | V5 用时 | V5 GFLOPS | 相对 V1 | 相对 V4 | V5 的 block 数 |
|---|---|---|---|---|---|
| 337³ | 0.058 ms | 1318.7 | 2.13× | **0.65×** | 9（24 SM 用 37%） |
| 256×512×256 | 0.042 ms | 1598.4 | 2.58× | **0.67×** | 8（33%） |
| 2048³ | **2.032 ms** | **8456.7** | **8.51×** | **1.38×** | 256 |
| 8864×8864×7931 | **169.977 ms** | **7332.1** | **9.00×** | **1.46×** | 4900 |

2048³ 的 8.46 TFLOPS = **52.9% 的 FP32 峰值**；修完冲突后 FMA 管道利用率从 57.5% 升到 **61.6%**，LSU 44.7%。

### 6.7 为什么 V5 大尺寸掉 13%，而 V3 只掉 6%？

| 版本 | 2048³ | 8864³ | 跌幅 | 每 SM 驻留 block |
|---|---|---|---|---|
| V1 | 993.8 | 814.6 | −18.0% | 1 块 / 1024 线程 |
| V2 | 843.6 | 781.1 | −7.4% | 1 块 / 1024 线程（高 MLP 载入） |
| V3 | 3437.2 | 3229.6 | **−6.0%** | **4 块 / 1024 线程** |
| V4 | 6134.3 | 5017.7 | −18.2% | 2 块 / 512 线程 |
| V5 | 8456.7 | 7332.1 | **−13.3%** | 2 块 / 512 线程 |

原因可以拆成两条：

1. **占用率**：工作集超过 L2 后，取数延迟从 ~200 周期涨到 400~600 周期。V3 有 32 个 warp 可换，V4/V5 只有 16 个，更容易「全员都在等」。
2. **全局流量**：V4 每秒要从 L2/DRAM 拉 `5018 GFLOPS ÷ 16 flop/B ≈ 314 GB/s`，是五版里最高的；V5 虽然更快，但它是 32 flop/B，只有 `7332 ÷ 32 ≈ 229 GB/s`；V3 是 `3230 ÷ 16 ≈ 202 GB/s`。流量越高、越容易在大尺寸下撞墙。

所以 V5 的 −13% 是「占用率低 + 流量中等」的结果，而 V3 的 −6% 来自「占用率高 + 流量最低」。

### 6.8 V5 的软肋：小题大做

V5 的 tile 是 128×128：

- 337³ → grid 3×3 = **9 个 block**；
- 256×512×256 → grid 4×2 = **8 个 block**；
- 但 GPU 有 **24 个 SM**。

一半以上的车间在闲着，所以这两个小形状 V5 反而输给 V4（0.65× / 0.67×）。

> **一句话记住：tile 越大，单个 block 效率越高，但需要更大的题目才能喂饱所有 SM；而且 64 个累加器会把占用率压到 2 块/SM。**

## 8. 官方 cuBLAS 为什么还更快？

### 8.1 数字

| 形状 | cuBLAS FP32 | V5 | V5 达到 cuBLAS 的比例 |
|---|---|---|---|
| 2048³ | 1.831 ms / 9383.2 GFLOPS | 2.032 ms / 8456.7 | **90.1%** |
| 8864×8864×7931 | 113.792 ms / 10952.3 GFLOPS | 169.977 ms / 7332.1 | **66.9%** |

- cuBLAS 越大越快：9.38 → 10.95 TFLOPS（+17%）；
- V5 越大越慢：8.46 → 7.33 TFLOPS（−13%）。

### 8.2 用厨房打比方

- **V5**：一个厨师，先跑去仓库把这一段的料全搬回来，再开始炒；炒完再跑去搬下一段。搬的时候灶台是冷的。
- **cuBLAS**：流水线厨房。有专门的搬运工**提前把下一段料送到**（双缓冲），厨师只管炒；厨房还会根据订单大小自动换布局（autotune），并且把同时开工的班组安排在同一片取货区（block swizzle）。

### 8.3 具体差在哪

1. **没有双缓冲 / 异步拷贝（最大差距）**
   V5 的节奏是 `搬料 → 同步 → 炒菜 → 同步`，显存延迟每段都裸露；
   cuBLAS 用 `cp.async`（Ampere 起的异步拷贝）把「搬下一段」和「炒当前段」重叠起来。

2. **占用率 / 延迟容忍**
   V5 每 SM 只有 2 个 block（16 个 warp）；大尺寸时数据不在 L2 里，延迟变长，没有足够的 warp 来填空。
   V3 有 4 个 block，所以它在大尺寸下只掉 6%，而 V5 掉 13%。

3. **Block swizzle（L2 友好重排）**
   cuBLAS 会调整 block 的执行顺序，让同时开工的 block 尽量共用 A/B 数据，提高 L2 命中率；V5 是默认顺序。

4. **全局读写向量化**
   V5 的 tile 载入还是标量 `LDG` / `STS`；cuBLAS 用 `LDG.128` / `cp.async` 16 B，指令更少。

5. **手调 SASS + 按形状选 kernel**
   cuBLAS 是逐架构手调的机器码，并且会根据 M/N/K 自动选 tile 大小、stage 数、是否 split-K。
   V5 是一套固定配置，靠 nvcc 编译。

### 8.4 为什么大尺寸差距更大？

- 2048³ 的数据还能较多地命中 L2，V5 的短板被掩盖；
- 8864³ 时工作集远超 L2，显存延迟成为主角。V5 没有流水线来藏延迟，cuBLAS 有。
- 结果：cuBLAS 的 FMA 利用率从 58.6% 涨到 68.5%，V5 从 52.9% 掉到 45.8%。

> **一句话记住：V5 差的不再是「算得对不对、搬得省不省」，而是「等的时候有没有别的事干」。**

## 9. 天花板：FP32 GEMM 最快能到多少？

### 9.1 两个上限，取小的那个

1. **算力上限**：24 SM × 128 核 × 2 flop × 2.6 GHz ≈ **16 TFLOPS**；
2. **共享内存数据上限**：全 GPU 约 **8 TB/s** 的 smem 读写带宽。

### 9.2 V5 到底要多少 smem 带宽？

ncu 实测每条 `LDS.128` 平均 **3 个 wavefront**（A 是广播、B 是 2 个），每个 wavefront 128 B：

```
每个 warp 每个 k 步：
  4 条指令 × 3 wavefront × 128 B = 1536 B
  同时做：64 FMA/线程 × 32 lane = 2048 次乘加
  → 1536 ÷ 2048 = 0.75 B/FMA
```

为什么比理论上的 1 B/FMA 小？因为 A 的 16 个 lane 读的是同一块数据（广播），硬件只需要搬一次。

于是 smem 侧上限：

```
8 TB/s ÷ 0.75 B/FMA ≈ 10.7 TFLOPS
```

### 9.3 对照

| | 实测 | 说明 |
|---|---|---|
| cuBLAS 大尺寸 | 10.95 TFLOPS | **基本贴着 10.7 的 smem 上限** |
| V5 2048³ | 8.46 | 上限的 79% |
| V5 大尺寸 | 7.33 | 上限的 68% |

想超过 10.7 TFLOPS，只有两条路：

- **更大的寄存器 tile**（比如 16×8，进一步降低 B/FMA）——寄存器会更紧张；
- **换精度走 Tensor Core**（TF32/FP16/BF16）——cuBLAS 的 TF32 能到 14.7~14.9 TFLOPS，但精度从 23-bit 尾数降到 10-bit。

> **一句话记住：FP32 的「手写天花板」大约 10~11 TFLOPS；cuBLAS 已经在门口，V5 还差 20~30%。**

## 10. 小白也能记住的 6 句话

1. **GPU 的瓶颈永远在「搬数据」**：寄存器 → smem → L1 → L2 → DRAM，越远越慢。
2. **GEMM 的数据是可以复用的**：同一个 A/B 数会被很多输出用到；优化的本质是提高复用、减少搬运。
3. **V2 的教训**：换一个更快的仓库（smem）不等于少跑几趟；**减少取数次数**才是关键。
4. **V3/V5 的手段**：让一个线程一次算很多输出（4×4、8×8），用寄存器把「读一次、用多次」做大。
5. **V4 的手段**：一条指令搬 4 个数（float4），减少的是「指令条数」。
6. **cuBLAS 的手段**：流水线（双缓冲/异步拷贝）+ 高占用率 + L2 重排 + 手调机器码；所以它在大尺寸下还能继续加速。

## 11. 术语表

| 术语 | 白话解释 |
|---|---|
| SM | GPU 的一个「车间」，本机有 24 个 |
| warp | 32 个线程组成的一组，同进同退 |
| lane | warp 里的一个线程 |
| FMA | 乘加运算 `a*b+c`，算 2 次浮点运算 |
| 寄存器 | 每个线程私有的最快存储 |
| smem（共享内存） | 一个 block 内共享的工作台，约 100 KB/SM |
| bank conflict | 32 个 bank 里，两个人要同一 bank 的不同地址，只能排队 |
| wavefront | 共享内存一次能处理的一批请求（约 128 B） |
| LDS.128 / float4 | 一条指令读 16 字节（4 个 float） |
| 寄存器分块 | 一个线程一次算多个输出，把复用的数留在寄存器里 |
| B/FMA | 每做一次乘加，平均要搬多少字节 |
| 算术强度 AI | 浮点运算次数 ÷ 搬运字节数 |
| 拐点 | 峰值算力 ÷ 显存带宽 ≈ 62 flop/B；AI 大于它才偏计算受限 |
| 占用率 | 同时能驻留多少 warp（可用来隐藏延迟） |
| 波前量化 / wave quantization | block 数不是 SM 数的整数倍，导致部分 SM 闲着 |
| 双缓冲 | 一边算当前数据，一边提前把下一批数据搬进来 |
| cp.async | Ampere 起的异步拷贝：global → smem 不占用计算寄存器 |
| block swizzle | 调整 block 的执行顺序，提高 L2 命中率 |
| autotune | 官方库按问题形状自动选择 tile/block/流水线参数 |
