九句话：

1. **算术强度是题目属性**（= 1/(2(1/M+1/N+1/K))，方阵时 = N/6），不随机器 / 代码变化；「拐点」≈ **62 flop/B**（≈16.0 TFLOPS ÷ 256 GB/s，按内核实测频率 2595~2610 MHz 计，见 §1 修正记录）。
2. **想要最大带宽 = 把 K 压薄**：K≤4 后进入 ~200 GB/s 平台（约 80% 峰值），目前最高 209.3 GB/s（8192×8192×1）。
3. **这台笔记本的时钟档会制造 2 倍级性能波动**——每轮测量前先查插电 + 时钟（见 §2）。
4. **V2（smem tiling）正确但比 V1 慢**（2048³：20.282 vs 17.288 ms，0.85×；5832³ 与 6914×5579×8215 都是 0.95×——大尺寸下差距稳定收窄）——现代 GPU 的 L1 已能供 ~4 TB/s，「只加 smem、不加寄存器分块」没有收益；剖析见 §4、§3.4、§3.5。
5. **V3（寄存器分块）是分水岭**（2026-10-19）：2048³ **5.105 ms / 3365.5 GFLOPS = 3.39× V1**，smem 读 8 → 2 B/FMA；大尺寸 8864×8864×7931 仍 **3265.9 GFLOPS = 4.00× V1**（几乎不掉，−3.0%）——**换存储层次救不了，减少取数次数才救得了**（§5）。
6. **修掉 bank conflict 后，下一堵墙是「LSU 指令条数」**（2026-10-19）：冲突 134,217,728 → **0**、wavefronts ÷2，但 2048³ 只从 5.105 → **4.995 ms（+2.2%）**——ncu 里 `sm__inst_executed_pipe_lsu` = **98.25%**，数据通路只用 ~43%；每 k 步 8 条 LDS / 16 条 FFMA 的指令比例才是瓶颈。下一步靠 `float4` 与 8×8 减少内存指令条数（§5.6、§5.7、§5.8）。
7. **float4 向量化再砍一刀**（2026-10-19）：V4 用 **2 条 LDS.128** 替换 8 条 LDS.32 → 2048³ **2.798 ms / 6141.0 GFLOPS = 1.79× V3、6.18× V1**；LSU 98.25% → **59.25%**，FMA 21% → **40.97%**，但 REG 87 让占用率掉到 2 块/SM（§5.7）。
8. **8×8 + float4 再进一步**（2026-10-19）：V5 2048³ **2.032 ms / 8456.7 GFLOPS = 1.38× V4、8.51× V1**（52.9% 峰值）；但 128×128 的 tile 让小矩阵只剩 8~9 个 block（24 SM 闲置）——**大矩阵专用**：8864×8864×7931 上 169.977 ms / **7332.1 GFLOPS = 9.00× V1、1.46× V4**（§5.8）。
9. **双缓冲不是免费的**（2026-10-19）：V6 用 cp.async 把载入与计算流水化，逻辑全 PASS，但 2048³ **2.086 ms vs V5 1.932 ms（0.93×）**、8864³ **209.4 vs 189.3 ms（0.90×）**——4 B cp.async 吞吐低、smem 翻倍把 carveout 从 65.5 推到 102.4 KB（L1 少约 37 KB）；当前瓶颈不是 global 延迟，2 块/SM 已经够藏（§5.10）。

## 1. 程序与成绩单口径

V1 naive 结构：

- 映射：`i = blockIdx.y·32 + threadIdx.y`（C 的行）、`j = blockIdx.x·32 + threadIdx.x`（C 的列）；grid 的 x 盖 N、y 盖 M。
- 每线程：`acc = Σ_{k<K} A[i][k]·B[k][j]`，循环外写回一次 C。
- 对拍：**容差**（1e-3 相对 + 1e-3 绝对）——GEMM 有浮点累加，GPU/CPU 顺序不同，不能用 `==`。
- 数据：0.25 步长小整数（值域 [-2,2]），K ≤ 4096 时所有部分和可被 float 精确表示。

**成绩单三行（本 readme 所有表格的口径）**——即「可以加一个带宽显示吗」的实现结果：

- **最小流量** = 4(MK + KN + MN) 字节（A、B 各读一遍 + C 写一遍，任何实现的下界）
- **有效带宽** = 最小流量 ÷ 实测时间
  - ⚠ 它不是"硬件真实流量"：实现若有读放大，真实流量 ≥ 最小流量（真实值要用 ncu 看）
  - 换算关系：有效带宽 = GFLOPS ÷ 算术强度
- **算术强度 AI** = 2MNK ÷ 最小流量 = **1 / (2(1/M + 1/N + 1/K))**；方阵时 = N/6
- **DRAM 下限** = 最小流量 ÷ 256 GB/s；它的"占实测 %"是**离内存墙有多近的体温计**（越接近 100% 越贴近带宽墙；大 K 时只有 1%）
- 拐点（roofline 分界）= FP32 峰值 ÷ 带宽 ≈ **62 flop/B**（AI > 62 → 计算侧；AI < 62 → 带宽侧）
  - FP32 峰值 = 24 SM × 128 核 × 2 × ≈2600 MHz（kernel 运行期实测稳定频率 2595~2610）≈ **16.0 TFLOPS**
  - 带宽 = 256 GB/s（128-bit × 16 Gbps；`nvidia-smi` 最大显存时钟 8001 MHz 复核）
  - ⚠ **修正记录（2026-10-15 复核）**：旧值 **56** 用的是 2340 MHz 档（14.4 TFLOPS）；规格 boost 2.37 GHz 口径则得 **57**——都不代表本机负载下能跑到的频率。拐点随档位滑动（1890→45 / 2340→56 / 2600→62），是「带」不是常数

**本次会话修掉 / 待修的小坑：**

- `calloc((size_t)out_bytes, sizeof(float))` 曾多分配 4 倍内存，已改为 `calloc((size_t)M * N, sizeof(float))`
- K=1 时算术强度 0.5 被 `%.0f` 显示成 `0` → 建议改 `%.1f`
- 子目录 CMakeLists 的 `CUDA_SEPARABLE_COMPILATION ON` 对单文件用不上（会给 nvcc 加 `-rdc=true` + 多余设备链接步骤），可删

> **结构注记（2026-10-19）**：成绩单改为 `report(name, kernel)` lambda —— 每个 kernel 跑完**立刻**拷回 + 对拍 + 打印，再跑下一个。原因：`d_out` 只有一块，旧写法（两个 kernel 都跑完再统一验）实际只验到了最后一个 kernel。

## 2. 测量方法：本机时钟档（重要！）

**现象：同一份二进制、同样参数，两次运行可以差 2 倍。**

本次实录（2048³）：

| 运行 | best | GFLOPS | 说明 |
|---|---|---|---|
| 改代码前 | 19.166 ms | 896.4 | 高频档 |
| 改代码后首跑 | 40.088 ms | 428.6 | 低频档（当时以为"变慢了"） |
| 复测 #1（iters=100） | 17.288 ms | 993.7 | 高频档 |
| 复测 #2（iters=20） | 17.287 ms | 993.8 | 高频档（两遍只差 0.001 ms） |

代码改动只有 host 侧（calloc、printf），**不可能影响 kernel 计时**（cudaEvent 只包 kernel）→ 变量是**机器状态**。

**采样证据**（kernel 运行期间每 0.4s 采一次 GPU）：

```
CPU 参考阶段： 210 MHz / ~3 W / 0%（GPU 完全闲置）
kernel 阶段：  1890 → 2595 MHz，功耗 10 → 68 W，利用率 99%（约 1 秒内爬满）
```

注意：kernel 启动的头几十毫秒可能还踩在时钟爬坡段上——**短窗口（iters 太少）+ 冷启动**更容易拿到偏慢的数字；热身一遍再正式跑可以缓解。

**测量仪式**（每次对比前固定执行）：

```bash
cat /sys/class/power_supply/AC1/online                       # 必须 = 1（插电）
nvidia-smi --query-gpu=clocks.sm,clocks.max.sm,power.draw --format=csv,noheader
./build/bin/GEMMkernel <M> <N> <K> 100                       # 先热身/正式都用大 iters
```

- 对比测试必须同一档位、交叉测量；数字与当时的时钟档一起记录（沿用 transpose readme 的规矩）。
- 碰到异常慢先重跑：恢复 → 状态问题；仍异常 → `nvidia-smi -q -d PERFORMANCE` 看 slowdown 原因。
- ⚠ 后台 GPU 占用也会干扰：复核采样里见到 kernel 之外还有一段 570~600 MHz / 25~41% 的杂散活动（疑似桌面合成器）——测量时尽量让屏幕安静；数字异常时先看一眼有没有别的进程在用 GPU。

| 形状 | AI | best | GFLOPS | 有效带宽 | DRAM 下限占比 |
|---|---|---|---|---|---|
| 337³ | 56 | 0.090 ms | 848.8 | 15.1 GB/s | 5.90% |
| 1024³ | 171 | 2.184 ms | 983.1 | 5.8 GB/s | 2.25% |
| 2048³ | 341 | 17.288 ms | 993.7 | 2.9 GB/s | 1.14% |

- 吞吐随规模上升（6.2% 峰值 @2048³），小规模被固定开销拖累。
- ⚠ 再放大到 5832³ 反而回落到 5.1% 峰值（817.1 GFLOPS）——首次出现"越大越慢"，见 §3.4。
- ⚠ 1024³ 早期曾用 iters=1 测到 3.015 ms / 712 GFLOPS——短窗口踩到时钟爬坡段，已作废；统一用 iters=100。

### 3.2 贴拐点实验（AI ≈ 56 的两组）

**256×512×256（AI = 51）**——"长方形怎么调到拐点附近"：

```

```

**337×337×337（AI = 56.2）**——贴近拐点（按修正后 62 计，略偏内存侧）：

```
GEMM V1 native best =     0.090 ms,    848.8 GFLOPS, 有效带宽 =  15.11 GB/s
算术强度 56 flop/B；DRAM 下限 0.005 ms（占实测 5.90%）
verify: PASS
```

**372×372×372（AI = 62.0）**——按修正口径，真正落在拐点线上的方阵：

```
M1 is a 372 x 372 matrix, M2 is a 372 x 372 matrix,out is a 372 x 372 matrix
Total memory required is 1.6 MB
Grid size: 12 x 12, Block size: 32 x 32
GEMM V1 native best =     0.116 ms,    889.8 GFLOPS, 有效带宽 =  14.35 GB/s
算术强度 62 flop/B；DRAM 下限 0.006 ms（占实测 5.61%）
verify: PASS
```

- 意义的直观化：AI → 拐点时**两个理论下限趋于相等**——256×512×256（AI=51）是 DRAM 5.1µs vs 计算 4.2µs；337³（AI=56）是 5.3µs vs 4.8µs；372³（AI=62）两者都 ≈ 6.5µs。
- 但实测（111µs / 90µs / 116µs）仍离下限 ~17-22 倍：**拐点只决定「哪面墙离得近」，不决定你能贴多近**（这几组 1.3~1.7MB 全在 L2 里，0.1ms 基本全是开销）。

### 3.3 带宽侧扫描：薄 K（"长方形怎么调才能最大带宽"的答案）

固定 M=N=4096（C=64MB，总量已远超 L2），只扫 K：

| K | AI | best | 有效带宽 | DRAM 下限占比 |
|---|---|---|---|---|
| 1 | ~0.5 | 0.332 ms | **202.4 GB/s** | 79.1% |
| 2 | 1 | 0.337 ms | 199.4 GB/s | 77.9% |
| 4 | 2 | 0.352 ms | 190.9 GB/s | 74.6% |
| 8 | 4 | 0.526 ms | 128.1 GB/s | 50.0% |
| 16 | 8 | 1.047 ms | 64.6 GB/s | 25.2% |

再放大到 8192×8192×1：

```
GEMM V1 native best =     1.283 ms,    104.6 GFLOPS, 有效带宽 = 209.29 GB/s
算术强度 0 flop/B；DRAM 下限 1.049 ms（占实测 81.75%）
verify: PASS
```

**四个发现：**

1. 有效带宽随 K 减小**单调上升**，K≤4 后进入 ~190-210 GB/s 平台（≈80% 峰值）——从最早 256×512×256 的 11.9 提升到 209.3，**17 倍**。
2. ⚠ **「半薄」的 K=8~16 是个坑**：AI 已经过了拐点资格线，带宽却只有 65~128——V1 的每个 k 迭代都要等一次 B 行的加载（一个 block 的 32 个 warp 全在读同一行 B，同进度一起等，延迟藏不住；K 越大等得越多次）。这也是 8192×16 比 4096×16 好的原因（固定开销被摊薄：88.7 vs 64.6）。
3. K=1 时 GEMM 退化为外积 $C = a \otimes b$——本质就是"读两个向量、写一个大矩阵"的纯搬运题，所以带宽能冲顶。
4. DRAM 下限占比 1% → 82%：大 K 是"计算受限"，K≤4 是"贴着内存墙跑"。**AI ≤ 拐点只是资格线，能不能吃满带宽还要看实现延迟。**

### 3.4 超大尺寸：5832³（2026-10-19，默认 iters=20）——吞吐回落，V2 差距缩到 5%

```text
M1 is a 5832 x 5832 matrix, M2 is a 5832 x 5832 matrix,out is a 5832 x 5832 matrix
Total memory required is 389.2 MB
Grid size: 183 x 183, Block size: 32 x 32
GEMM V1 native best =   485.506 ms,    817.1 GFLOP/S, 有效带宽 =  0.84 GB/s, verify: PASS
GEMM V2 smem best =     511.360 ms,    775.8 GFLOP/S, 有效带宽 = 0.80 GB/s, verify: PASS
V2 相对 V1 加速比 = 0.9494x（>1 表示 V2 更快）
算术强度 972 flop/B；DRAM 下限 1.594 ms（V1 占实测 0.33%，V2 占实测 0.31%）
```

> `Total memory required is 389.2 MB` 是 MiB 口径（程序按 1024² 换算）：实际 3 × 136.0 MB = **408.1 MB**。

**规模数字：**

| 项目 | 值 |
|---|---|
| 乘加次数 | 5832³ ≈ 1.98 × 10¹¹ |
| FLOPs | 2 × 5832³ ≈ **396.7 GFLOP** |
| 单阵 | 5832² × 4 B = **136.0 MB** ≈ 5.7 × L2（24 MiB） |
| 三阵（A/B/C） | **408.1 MB** ≈ 17 × L2 |
| AI | 5832/6 = **972 flop/B**（拐点的 15.7 倍） |
| DRAM 下限 | 1.594 ms，占实测 **0.33%**（离内存墙约 300 倍） |

**对比 2048³（同一二进制、同一测量仪式）：**

| 形状 | V1 best | V1 GFLOPS | V2 GFLOPS | V2/V1 |
|---|---|---|---|---|
| 2048³ | 17.288 ms | 993.7 | 847.0 | 0.852 |
| 5832³ | 485.506 ms | **817.1** | **775.8** | **0.949** |
| 变化 | — | **−17.8%** | −8.4% | — |

- 体积 ×23.09，时间 ×28.08 → **每单位工作量慢 21.6%**。
- 相对 FP32 峰值 5.1%（817.1/16000）；相对「L1 天花板」（7.4 TB/s ÷ 4 B/flop ≈ 1.85 TFLOPS）只有 44%（2048³ 是 54%）。

**为什么掉？两个候选，都要验证：**

1. **L2 红利消失（尺寸相关）。** V1 每 block 从全局真实读 2 × 32×K×4 B = 1.49 MB，全 kernel ≈ **50 GB 读请求**（≈103 GB/s 请求率——注意这不是成绩单里那个 0.84 GB/s 有效带宽）。
   - 2048³：A、B 各只有 16 MiB，**能塞进 24 MiB L2** → 跨 block 的重复读基本被 L2 接住，L1 miss 的代价 ≈ L2 延迟。
   - 5832³：B 一个矩阵 136 MB（5.7 × L2）→ 每个 y 行都要重新扫一遍全部 B（136 MB），183 个 y 行合计 ≈ 25 GB；A 同理 → L1 miss 更多直落 DRAM，延迟暴露变多。
   - **证据：V2 只掉 8.4%，V1 掉 17.8%**（而且 V2 是后跑的、热状态更差）。V2 的全局读集中在载入段、1024 线程齐发（MLP 高），对 DRAM 延迟不敏感；V1 的读混在 FMA 循环里，依赖链上独立 load 少。
2. **持续满载的时钟下降（时长相关）。** 单次 kernel 485 ms、连跑 21 次，比 2048³（17 ms）更容易撞功耗/温度墙；若 L1 供给率不变，817/994 对应 ≈ 2600 × 0.82 ≈ **2.1 GHz**。

**区分实验（下次）：**

```bash
# ① 5832³ 运行时另开终端，1s 采样时钟
nvidia-smi --query-gpu=clocks.sm,power.draw,temperature.gpu --format=csv -l 1
# ② 让 2048³ 也持续满载：101 × 17 ms ≈ 1.7 s
./build/bin/GEMMkernel 2048 2048 2048 100
```

- 2048³ iters=100 若也掉到 ~820 GFLOPS → 主因是**功耗/温度墙**（与尺寸无关）；
- 若仍是 ~990 → 主因是**工作集超 L2**。

**没变的结论：**

- AI 972、DRAM 下限占比 0.33% → **掉速与带宽无关**；有效带宽 0.84 GB/s 只是"最小流量 ÷ 时间"的口径，真实读请求率上界 ≈103 GB/s（约 40% 峰值）。

## 4. V2：smem tiling 实测（2026-10-19）——正确，但比 V1 慢

### 4.1 实现要点

- `GEMMkernel_v2_smem`：32×32 线程块，每块认领 C 的 32×32 小块；`As` / `Bs` 各 32×32（合计 8 KB smem）。
- 沿 K 方向每 32 一段循环：载入两块 tile（**越界零填充**）→ `__syncthreads()` → 块内累加 → `__syncthreads()`。
- 方形版的载入是「一人一格」（1024 格 = 1024 线程，无需循环）：
  - `As[ty][tx] = A[i][kt + tx]`（行 → M 方向，列 → K 方向）
  - `Bs[ty][tx] = B[kt + ty][j]`（行 → K 方向，列 → N 方向）
- 理论收益：每 FMA 的**全局**字节从 ~8 B 降到 ~0.25 B（tile 在块内被复用 32 次）。

### 4.2 正确性：四组全 PASS（含边界与长方形）

| 256×512×256（长方形） | 0.111 ms | 0.126 ms | 1.14×（慢 14%） |
| 2048³ | 17.288 ms | 20.282 ms | 1.17×（慢 17%） |
| 5832³ | 485.506 ms | 511.360 ms | 1.05×（慢 5%） |
| 6914×5579×8215 | 779.676 ms | 818.460 ms | 1.05×（慢 5%） |

### 4.3 为什么 V2 反而慢（本练习最有价值的一课）

**一句话：V2 没有减少「每个 FMA 要取两个操作数」，它只是把取数从 L1 搬到了 smem；而 V1 的取数本来就被 L1 喂饱了。V2 砍的病，现代 GPU 上不存在。**

#### 4.3.1 先算 V1 的账：它根本不缺全局带宽

- 2048³：FMA 8.59 × 10⁹ 次，每次 2 个 4 B 操作数 → 1.72 × 10¹⁰ 次读 = **68.7 GB**；17.288 ms 吃完 ≈ **3.97 TB/s**。
- 本机 L1 聚合带宽 ≈ 24 SM × 128 B/clk × 2.4 GHz ≈ **7.4 TB/s** → V1 只用了 **54%**，离墙还远。
- 真正打到 L2/DRAM 的只有每块的 tile：2 × 32 × K × 4 B = 524 KB × 4096 块 ≈ **2.1 GB（≈124 GB/s，连 DRAM 峰值一半都不到）**。
- 结构原因：`m1[i*K+k]` 在一个 warp 内是**同地址广播**（1 次事务服务 32 个 lane），`m2[k*N+j]` 是**行内连续**（128 B 合并事务）→ L1 命中率极高，V1 实际上已经在「smem 速度」上取数了。

#### 4.3.2 V2 换的是取数位置，不是取数次数

- 内层仍是 `2 次读 + 1 次 FMA`（`As[ty][k]`、`Bs[k][tx]`）；
- LDS 与 L1 是**同一块物理 SRAM、同一套 LSU**，吞吐同为 ~128 B/clk/SM；
- 68.7 GB 的读需求一字节没少，只是地址空间从 global 变成 smem；
- 而且这份 smem 访问已经**完全无冲突**（As 广播、Bs 连续）——做到 smem 最优形态仍慢，说明病灶不在冲突；
- V2 相对「无缓存的 naive」把全局读从 68.7 GB 降到 ~2.1 GB，但 **V1 靠 L1 早已免费做到了同样的 2.1 GB**。

#### 4.3.3 V2 新增的成本（对着代码看）

| 成本 | 对应代码 | 2048³ 的量级 |
|---|---|---|
| 多一趟 global→寄存器→smem 的写 | `As[ty][tx] = ...` | 每线程每段 2 次 store |
| 全块栅栏 ×2/段 | 两个 `__syncthreads()` | 64 段 × 2 = **128 次/块**；每 SM 顺序跑 ~171 块 → ~2.2 万次 |
| 每 SM 只能驻 1 块 | 1024 线程 vs Ada 上限 1536 | 栅栏时**整个 SM 停摆**，没有第二块填缝 |
| 载入与计算被栅栏硬隔开 | `load → sync → compute` | global 延迟在载入段裸露；V1 的 load 与 FMA 交错，靠 32 warp 的 TLP 藏 |

```
V1:  load(k) ──┐
               ├── FMA(k) ── load(k+1) ── FMA(k+1) ...     ← 无栅栏，各 warp 自由流水
V2:  load tile ──[ sync：等最慢的那个 load ]── compute 32 步 ──[ sync ]── ...
                    ↑ 这期间整个 SM 无事可做
```

粗略量级：每段计算 = 1024 线程 × 32 FMA ÷ 128 FMA/clk ≈ **256 周期**；一次 tile 载入的延迟（L2 ~200 周期、DRAM ~500+）很容易把这一段拖长几十个百分点。实测只慢 17%，是因为多数载入命中 L2、32 个 warp 的 load 也有重叠——但气泡是结构性的。

#### 4.3.4 为什么教程里 V2 能快 3~8 倍

- 老 GPU（Fermi/Kepler 早期）**L1 不缓存 global**（或极小），naive 每次都在打 L2/DRAM，几百周期的延迟直接摊在 FMA 上；
- 那些教程的 tiling 通常还叠加了**寄存器分块**（每线程 4×4 / 8×8 输出），收益大头在那儿；
- Volta 起 L1 与 smem 合并为同一块 SRAM 且能缓存 global → naive 的「重复读」被硬件自动接住，软件 staging 变成重复劳动。
- 一句话：**V2 砍对了（教科书时代的）病，但你的 GPU 上这病已经不存在了。**

#### 4.3.5 数据自证：V2 从没赢过，胜利条件也不在它手里

| 形状 | V2/V1 | V1 GFLOPS | V2 GFLOPS |
|---|---|---|---|
| 337³ | 1.38× 慢 | 848.8 | 447.9 |
| 2048³ | 1.17× 慢 | 993.7 | 847.0 |
| 5832³ | 1.05× 慢 | 817.1 | 775.8 |
| 6914×5579×8215 | 1.05× 慢 | 812.8 | 774.3 |

- 规模越大差距越小，是因为 **V1 的缓存红利变薄**；
- 同时 **V2 自己的绝对吞吐也在掉**（847 → 776）——不是「大矩阵时 V2 变强」，而是「V1 变弱，追上了 V2」；
- 337³ 惩罚最大（38%）：K=337 → 11 段 × 32 = 352，最后一段只有 17/32 有效（约 4.3% 的乘加浪费在零填充上），而栅栏一次没少。
- 256×512（14%）与 2048（17%）的差距都在「同步 + 多一趟搬运」的固定成本量级上。

### 4.4 对下一步的意义

- V2 的价值不在成绩，而在于**用数据回答了「smem 到底救什么」**：它救「全局读延迟 / 带宽」，救不了「每 FMA 要取 2 个操作数」。
- 要赢 V1，必须减少**取数次数**：V3 寄存器分块（每线程 4×4 输出）→ 每个 k 步取 4+4 个操作数、做 16 次 FMA → smem 读从 8 B/FMA 降到 **2 B/FMA**（÷4），每次 sync 的「含金量」也 ×16；同时全局读减半（V1 是 8 flop/B，V3 是 16 flop/B）。
- 不改结构的小实验（可选）：32×16 / 16×16 小块（每 SM 驻 3~6 块，sync 停顿可被其他块掩护）；内层 `#pragma unroll`；双缓冲（V4 话题）。
- **V2 证明的是 smem 救不了什么；V3 才能验证 smem 能救什么。**
- **→ 已实现并实测**（2026-10-19）：三形状全 PASS，2048³ **5.105 ms / 3365.5 GFLOPS = 3.39× V1**（详见 §5）。

## 5. V3：寄存器分块实测（2026-10-19）——首次超过 V1

### 5.1 实现要点

- **block 16×16 = 256 线程，认领 C 的 64×64 小块**；每线程算 **4×4 = 16 个输出**（16 个寄存器累加器）。
- 沿 K 每 **16** 一段：`As[64][16]` + `Bs[16][64]` = **8 KB smem**（消冲突后 `As[64][17]`，共 8.25 KB）；载入 → sync → 计算 → sync。
- 每个 k 步：读 **4(A) + 4(B) = 8 次**，做 **16 次 FMA** → **2 B/FMA**（V1/V2 是 8 B/FMA，÷4）。
- 全局读：**(64+64)×16×4 B ÷ (64×64×16×2 flop) = 16 flop/B**（V1/V2 是 8，÷2）。
- 每 SM 可驻 **4 块**（1024 线程 / 上限 1536），栅栏气泡可被其他块掩护；V2 的 1024 线程块每 SM 只能驻 1 块。
- `acc[4][4]` 全程在寄存器；写回只在所有 k 段结束后做一次。
- bank conflict（2026-10-19 下半场已修）：原版 `As[64][16]` 的行间距 16 会让 ty=0/1 的两个地址落进同一 bank（2-way），`Bs[k][tx*4+j]` 的步长 4 也是 2-way；现改为 `As[64][17]` + `Bs[k][tx+16*j]` 交错映射，ncu 实测冲突归零（详见 §5.6）。

| V1 | 993.8 | 816.4 | **−17.9%** | +21.7% |
| V2 | 843.7 | 781.2 | −7.4% | +8.0% |
| V3 | 3365.5 | 3265.9 | **−3.0%** | **+3.0%** |

- 如果只是「时钟掉了 ~18%」，三个 kernel 应该**同比例**下降（FFMA、LDS、L1 带宽全部随 clk 走）——实测跌幅差 6 倍，**纯时钟解释基本出局**；
- 跌幅与「取数的延迟敏感度」单调对应：V1 的读混在 FMA 里（MLP 低、靠 L1 命中）→ −17.9%；V2 的全局读集中在载入段（高 MLP）→ −7.4%；V3 的操作数读取又少 4 倍 → **−3.0%**；
- **这就把 §3.4/§3.5 的归因基本闭环了**：大尺寸掉速的主因是缓存/延迟，而不是时钟（`clocks.sm` 采样仍可做最终确认）；
- 附带结论：**减少每 FMA 的取数次数，不只提高峰值，还让性能对工作集大小不再敏感**——V3 以后可以直接用 2048³ 的 ~3.3 TFLOPS 预估大矩阵；
- V3/V1 = **4.0004×**（几乎正好 4 倍），与 2 B/FMA 的账一致。

### 5.6 消 bank conflict 实测（2026-10-19 下半场）——修对了，但不是当前的那堵墙

**改动（3 行）：**

```cuda
__shared__ float As[BM][BK + 1];       // stride 17：ty=0/1 的两个地址不再同 bank
b[j] = Bs[k][tx + V3_BLOCK * j];       // B 列交错：16 lane 覆盖 16 个不同 bank
```

1. **`float4` 向量化**：B 改回连续 4 列 + `float4` 读；A 转置成 `As_t[BK][BM+4]` + `float4` 读 → 每 k 步 8 条内存指令降到 **2 条**；数据仍是 2 B/FMA → 上限 ~8 TFLOPS（约 2.3×）。**→ 已实现并实测：1.79× V3（§5.7）。**
2. **8×8 寄存器分块**：16 条 LDS / 64 FMA（0.25 条/FMA，减半），上限同样 ~8 TFLOPS；代价是 ~90+ 寄存器、占用率降到 2 块/SM。
3. **全局载入/写回向量化**（LDG.128 / STS.128）：只占内存指令的 ~11%，顺手做。

### 5.7 V4：float4 向量化实测（2026-10-19）——把 8 条 LDS 压成 2 条

**实现要点（分块参数与 V3 完全相同，只改取数）：**

- A **转置**存进 `As_t[BK][BM+4]`（16×68 字）：`As_t[c][r] = A[row0+r][kt+c]`；计算时 `As_t[k][4ty..4ty+3]` 是连续 4 个数 → 一条 `LDS.128`。
- B 保持 `Bs[BK][BN]`：`Bs[k][4tx..4tx+3]` 连续 → 一条 `LDS.128`。
- 两个数组加 `__align__(16)`；行 stride 68 / 64 字（272 B / 256 B）都是 16 B 的倍数，`float4` 不会踩到未对齐地址。
- 每 k 步：**2 条 LDS.128 + 16 条 FFMA**（V3 是 8 条 LDS.32）；写回列恢复连续的 `tx*4 + j`。

**成绩（Release，iters=100，三形状全 PASS）：**

### 5.8 V5：8×8 寄存器分块 + float4（2026-10-19）——8.46 TFLOPS，但只适合大矩阵

**实现要点：**

- 线程块 16×16 = 256，每线程 **8×8 = 64 个输出** → block tile **128×128**；BK 仍为 16。
- smem：`As_t[BK][128+4]`（16×132 字 = 8448 B）+ `Bs[BK][128]`（8192 B）= **16.25 KB**。
- 每 k 步：A 读 **2 条 LDS.128**（8 行）、B 读 **2 条 LDS.128**（8 列），做 **64 次 FMA**。
  → 内存指令 **0.0625 条/FMA**（V4 是 0.125），数据 **1 B/FMA**（V4 是 2）。
- `__launch_bounds__(256, 2)`：REG 正好 128，无 spill，每 SM 2 块（占用率 32%）。

**B 读的 bank conflict（已修，原版代码以注释保留）：**

- 原版：每线程连续 8 列，`Bs[k][tx*8 + {0,4}]`。16 个 lane 的步长是 8 字（32 B），只落在 4 个 bank 组上、每组被 4 个 lane 复用 → **4-way conflict**（ncu：33,554,432 次）。
- 修正：拆成两段 4 列——`Bs[k][4tx + {0..3}]` 与 `Bs[k][64 + 4tx + {0..3}]`，lane 步长变成 4 字（16 B）。写回列映射同步改成 `j<4 ? 4tx+j : 64+4tx+(j-4)`。
- 原版的 b0/b1 读和写回 `col = col0 + tx*8 + j` 都以注释形式留在代码旁边，并注明原因。

### 5.10 V6：cp.async 双缓冲（2026-10-19）——正确，但比 V5 慢 7~15%

**实现要点（与 V5 同 tile，只改载入方式）：**

- 分块完全沿用 V5：16×16 线程、每线程 8×8、block tile 128×128、BK=16。
- smem 开两段：`As_t[2][16][132]` + `Bs[2][16][128]` = **33,280 B/块**（V5 是 16,640 B）。
- 流水：
  ```
  预取 stage 0（cp.async + commit）
  for 每段 kt:
      异步预取下一段到另一个 buffer（cp.async + commit）
      cp.async.wait_group 1（还有下一段）/ 0（最后一段）
      __syncthreads()
      计算当前段（4 条 LDS.128 + 64 FFMA）
      __syncthreads()      // 读完才能覆盖
  ```
- 载入用 **4 B** 的 `cp.async.ca`：A 的全局地址是 `(row0+r)*K + kt + c`，K 不保证是 4 的倍数，16 B 对齐无法保证；越界用 `src_bytes=0` 让硬件零填充。
- `__launch_bounds__(256, 2)`；资源：REG 128、SHARED 33,280 B、LOCAL 0、**STACK 64 B**（V5 是 0）。

**成绩（本轮 Release，iters=100；8864 用 10；全部 PASS）：**

| 形状 | V5 | V6 | V6/V5 | V6 GFLOPS |
|---|---|---|---|---|
| 337³ | 0.058 ms | 0.069 ms | **0.85×** | 1115.7 |
| 256×512×256 | 0.043 ms | 0.050 ms | **0.86×** | 1340.9 |
| 2048³ | 1.932 ms | 2.086 ms | **0.93×** | 8236.7 |
| 8864×8864×7931 | 189.291 ms | 209.414 ms | **0.90×** | 5951.3 |

> ⚠ 本轮整体时钟偏低：同一轮 V1 在 8864³ 是 1794.8 ms，归档值是 1529.952 ms（约 −15%）。所以只比同轮 V6/V5，不跨轮比绝对时间。

**为什么双缓冲反而慢（ncu 实测）：**

1. **4 B cp.async 的吞吐低**：每段每线程 16 条 `cp.async`（A 8 + B 8），每条只搬 4 B；V5 是 16 条 LDG.32 + 16 条 STS.32。指令数看似减半，但 2048³ 的 LSU 指令数反而从 **25,305,088 → 26,609,664**（多出的是 commit/wait 与地址选择），FMA 管道里的整数指令从 **279,007,232 → 289,275,904（+3.7%，IMAD）**。
2. **smem 翻倍挤掉 L1**：`launch__shared_mem_config_size` 实测 V5 **65.54 KB** → V6 **102.40 KB**；Ada 的 L1/smem 是同一块 128 KB SRAM，carveout 多 37 KB，L1 就少 37 KB（约 62 → 26 KB，−58%）。V5 的全局读（2048³ 约 1.07 GB）很大一部分靠 L1/L2 接住，L1 变小让 global load 更容易打到 L2/DRAM。
3. **2 块/SM 已经把延迟藏住了**：V5 每 SM 2 个 block、16 warps，计算段 64 FMA/线程/k 很长；一个 block 在栅栏处停顿时，另一个 block 可以继续算/载入。显式流水的收益被块间并行覆盖，commit/wait/双缓冲地址计算成了净开销。8864³ 同样输 10%，说明不是「数据在 L2 所以不需要流水线」——数据不在 L2 时，V5 的 16 warps 也够藏。

**ncu 对比（2048³；ncu 下 cp.async 的 replay 会放大绝对时间，只看看利用率/指令数）：**

| 指标 | V5 | V6 |
|---|---|---|
| `pipe_fma` | 61.49% | 59.72% |
| `pipe_lsu` | 44.62% | 43.95% |
| LSU 指令数 | 25,305,088 | 26,609,664 |
| FMA 管道指令数（含 IMAD） | 279,007,232 | 289,275,904 |
| smem carveout | 65.54 KB | **102.40 KB** |
| smem/块 | 16.64 KB | 33.28 KB |
| 占用率限制（reg / smem） | 2 / 3 块 | 2 / 2 块 |
| REG / STACK / LOCAL | 128 / 0 / 0 | 128 / 64 B / 0 |

**结论与下一步：**

- V6 证明了一件事：**当瓶颈是「指令组合 + 占用率」而不是「global 延迟裸露」时，双缓冲是负优化**。
- 要让双缓冲有收益，得先把两个副作用消掉：
  - **B 换 16 B cp.async**：B 在 smem 里是连续的（`Bs[k][col..col+3]`），N%4==0 时可 16 B 对齐；A 因为转置布局（4 个连续 k 落在 4 个不同 smem 行）只能保持 4 B。每段 cp.async 从 16 → 10 条。
  - **BK=8 双缓冲**：每块 smem 回到 ~16.6 KB（与 V5 相同），carveout 保持 64 KB，L1 不被挤；代价是栅栏次数翻倍。
  - **3 段流水 + BK=8**：smem ~25 KB/块，2 块 50 KB 仍是 64 KB carveout，用更深流水换延迟容忍。
- 若目标是继续冲 GFLOPS，优先级可能不在流水线，而在 **8×4/4×8 提占用率**、**block swizzle 提 L2 命中**、**按尺寸派发 V4/V5**。

| 屏幕最后一行 | 说明它在 |
|---|---|
| `M1 is ...` / `Total memory ...` | 刚启动 / 造数据（之后进入长时间的 CPU 参考，静默） |
| `Grid size: ...` | CPU 参考已过，进入 GPU 阶段（很快） |
| `GEMM V1 native best = ...` | 完成 |

- 「CPU 占用低」：参考是**单线程**——进程自身 100% 单核，但整机监视器里只有 ~1/N；此时 GPU 反而是闲的（210 MHz / 3 W）。
- 缓解：改成 `-DCMAKE_BUILD_TYPE=Release` 重配（CPU 参考快约 20 倍）；对拍用 ≤2048；大 N 别用默认 iters 20。

### Q2「为什么算数强度下降这么多？」

- 两个概念被看成一个了：
  - **算术强度 = 题目属性**（同规模下恒定，如 2048³ 永远 341）——"341 → 51"不是下降，是**换了形状**；
  - **GFLOPS = 吞吐**（随机器状态波动）——896.4 → 428.6 那是**时钟档**（见 §2），与代码无关：同一份二进制复测 993.7 / 993.8。
- 所有数的关系一直自洽：有效带宽 = GFLOPS ÷ AI（896.4/341=2.63；428.6/341=1.26；993.7/341=2.91）。

### Q3「算术强度和 57 接近了，对吗？」（2026-10-15 复核：修正为 ≈62）

- 方向对，但拐点要修正（见 §1）：按本机实测频率口径为 **≈62**（16.0 TFLOPS ÷ 256 GB/s），不是 56 / 57。
- 256×512×256 的 AI = 51.2（比拐点低 ~17%，偏内存侧）；337³ 为 56.2（低 ~10%）；**真正「坐在线上」的方阵是 N ≈ 372**（已补测，见 §3.2）。
- 直观含义：AI → 拐点时两个理论下限趋于相等（372³：DRAM 6.5µs ≈ 计算 6.5µs）——这才是「坐在分界线上」。
- 通用公式 AI = 1/(2(1/M+1/N+1/K))。

### Q4「长方形怎么调才能最大带宽？」

- **配方：K 压到 1~4 + M、N 尽量大（C ≥ 64MB）。** 实测封顶 ≈ 200~210 GB/s（§3.3，最佳 209.3）。
- 对照本机历史：vector_add ≈ 250 GB/s（98%）、transpose V3 ≈ 200~211、reducemax ≈ 217——小 K GEMM 已进入同一梯队。
- 只压到"接近拐点"不够（K=16 只有 64.6）：见 §3.3 发现 2。
- 超过 256 GB/s 的数字 = 数据缩回 L2 的虚高，不算数（老规矩）。

### Q5（附录）「nvcc 直调」和「CMake」什么区别？

- CMake 最终也是调用 nvcc（可看 `build/GEMM/GEMMkernel/CMakeFiles/GEMMkernel.dir/build.make`）；区别是"谁来生成 / 管理这条命令"：CMake 管参数（C++17、arch 89、`-rdc=true`）、增量构建、统一输出 `build/bin`、给 IDE 出 `compile_commands.json`。
- nvcc 直调（`nvcc -O3 -arch=sm_89 -o gemm_v1 xxx.cu`）适合单文件快速试验；工程内统一用 CMake。

### Q6「5832³ 大概多久算完？」（预测 vs 实测）

- 预测：Debug 构建总时长 7~12 分钟，其中 ≥95% 是 CPU 参考（O(N³) 单线程、无优化）；GPU 两段合计 ~20 s。
- 实测（默认 iters=20）：GPU 段 = 21 × (485.5 + 511.4) ms ≈ **21 s** ✓；CPU 参考如预期是分钟级静默段（期间 GPU 210 MHz 闲置）。
- 唯一偏差在吞吐：预测按 2048³ 的 ~990 GFLOPS 线性外推 V1 ≈ 0.40 s/次，实际 0.486 s/次（817 GFLOPS）——**大尺寸下吞吐回落 18%**，剖析与验证方法见 §3.4。
- 提速：`cmake -S . -B build -DCMAKE_BUILD_TYPE=Release` 重配（CPU 参考快约一个量级；device 代码本来就优化，kernel 计时不受影响）；`iters` 调小只省 GPU 段（21 s → ~5 s）；先跑 4096³ 打样（Debug 下 CPU 参考约 2~3 分钟）。
- 后续（同日）：切 Release 后跑长方形 6914×5579×8215（§3.5）——CPU 参考缩到一两分钟，GPU 计时与 Debug 历史可比；V1 812.8 GFLOPS，与 5832³ 的 817.1 基本一致。

### Q7「为什么 V2 比 V1 还慢？」（2026-10-19 追问，完整数字账见 §4.3）

- 一句话：V2 没减少「每个 FMA 取两个操作数」，只把取数从 L1 搬到 smem；而 V1 的取数已经被 L1 喂饱（2048³：68.7 GB ÷ 17.3 ms = **3.97 TB/s**，仅为 L1 上限 7.4 TB/s 的 **54%**）。
- LDS 与 L1 是同一块 SRAM、同一套 LSU；68.7 GB 一分没少，还多了 smem 写入 + 每段 2 次全块栅栏（2048³ 每块 128 次，每 SM 约 2.2 万次）。
- 1024 线程块 → 每 SM 只驻 1 块，栅栏时全 SM 停摆、没有第二块填缝；载入段与计算段被隔开，global 延迟裸露（V1 的 load 与 FMA 交错，靠 32 warp 的 TLP 藏）。
- 教程里的 3~8× 来自「L1 不缓存 global」的老 GPU + 寄存器分块；现代 GPU 上 smem-only 打不过 naive。
- 数据：四种形状 V2 从没赢过；大尺寸差距缩小（1.38 → 1.17 → 1.05）是因为 **V1 的缓存红利变薄**，不是 V2 变强（V2 自己 847 → 776 GFLOPS）。

---

## 7. 结论与下一步

**九条经验线：**

1. 形状 → AI → **资格线**：AI ≤ 62 才谈得上带宽侧（大 K 形状 16000/AI 就是它的带宽天花板，如 2048³ 上限 ≈ 47 GB/s）；
2. 实现 → 延迟 → **能不能贴墙**：K=8~16 的延迟坑（AI 达标但带宽只有 65~128）说明 V1 的内循环还能再藏延迟——留给 ncu 验证（预期 long scoreboard）。
3. **smem 不是银弹**（2026-10-19）：V2 实测慢于 V1（见 §4）——「换存储层次」不如「减少取数次数」；后者才是 V3 要做的。
4. **大规模吞吐平台 ~815 GFLOPS**（2026-10-19）：工作集 ≫ L2 后，5832³ 是 817.1、6914×5579×8215 是 812.8、8864×8864×7931 是 816.4——V2 也同样停在 ~775，V2/V1 稳定 0.95。掉速原因曾是「L2 红利消失 vs 时钟掉 18%」的数值简并（993.7 × 0.82 ≈ 815）；但同日大尺寸下 V1/V2/V3 跌幅为 **17.9% / 7.4% / 3.0%**（§5.5），纯时钟解释被削弱，**缓存/延迟解释占优**；`clocks.sm` 采样仍可做最终确认（§3.4/§3.5）。
5. **寄存器分块是分水岭**（2026-10-19）：V3 2048³ **5.105 ms / 3365.5 GFLOPS = 3.39× V1**，smem 读 8 → 2 B/FMA；大尺寸 8864×8864×7931 仍 **3265.9 GFLOPS = 4.00× V1**（仅 −3.0%）（§5）——V2 的失败与 V3 的成功是同一枚硬币的两面：**换存储层次救不了，减少取数次数才救得了**。
6. **瓶颈会迁移**（2026-10-19）：V1 卡在 L1 带宽 → V2 卡在同步 → V3 卡在 LSU 指令条数。消掉 bank conflict（134M → 0）只换来 2.2%，因为每 k 步 8 条 LDS / 16 条 FFMA 的**指令比例**才是新瓶颈（`sm__inst_executed_pipe_lsu` = 98.25%）；下一轮靠 `float4`/8×8 让每条指令多干活（§5.6）。
7. **向量化是第二道分水岭**（2026-10-19）：V4 用 2 条 LDS.128 替换 8 条 LDS.32 → 2048³ **2.798 ms / 6141.0 GFLOPS = 1.79× V3、6.18× V1**；LSU 98.25% → **59.25%**，FMA 21% → **40.97%**；但 REG 87 让占用率掉到 2 块/SM，下一轮先调占用率（§5.7）。
8. **块越大，小题目越吃亏**（2026-10-19）：V5 的 128×128 tile 在 2048³ 上 8.46 TFLOPS（52.9% 峰值，1.38× V4），但 337³ / 256×512×256 只有 9 / 8 个 block（24 SM 用不满），反而输给 V4——**tile 大小要按题目规模选**；大尺寸 8864×8864×7931 上 7.33 TFLOPS（9.00× V1、1.46× V4），**2048³ 以上 V5 全面胜出**（§5.8）。
9. **双缓冲要看瓶颈**（2026-10-19）：V6 把「载入→同步→计算→同步」改成两段 cp.async 流水，反而慢 7~15%——4 B cp.async 的吞吐 + smem 翻倍挤掉 L1；V5 的 2 块/SM（16 warps）已经把 global 延迟藏住了，流水线只对「延迟裸露」有效。下一轮：B 换 16 B cp.async、BK=8 双缓冲保 carveout、或 8×4 提占用率（§5.10）。
